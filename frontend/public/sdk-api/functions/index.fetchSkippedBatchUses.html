      Find every batch the verifier landed with no use counted, and the claims and uses it carried. The verifier resolves a batch whose call to UsageCounter reverts whole (a period boundary crossed in flight, the last period closed (AccrualClosed), a provenance mismatch) and emits BatchAccrualSkipped(batchId, reason) (docs/DESIGN_DECISIONS.md § 19). A call its submitter starved of gas is never among them: the verifier reverts that batch whole (AccrualStarvedOfGas), so it lands nothing and no log of it exists. In the same transaction it logs the batch's operation stream in BatchOperations(batchId, …), however the call reached it, and the stream carries each usage claim whole (usageClaimsOfOperationStream). So the answer is read from the verifier's logs alone: no transaction is read, and a settleBatch call made through another contract is read as a direct one is.

      Each use stays uncounted and a later batch may prove it again while a period is open; reason tells the caller whether sending again can work (AccrualClosed is final). Anyone can send each claim in carried.claims again with SequencerClient.submitUsageClaim, without the agreement. carried.uses are the uses the guest derives from those claims (apply_usage_claims, prover/lib/src/kernel.rs): one per (kind, key, process, seller), in claim order, a root order's process id derived under the verifier's EIP-712 domain (the client's chain id and batchVerifier); the proof binds them to the settleBatch argument. A use the counter skips one by one inside a call that does not revert (an unstaked seller, a key without a live registration, a seller of a process already counted, a process already a use of its process design in an earlier period) emits no event, and this reader does not see it; UsageCounter.sellerCounted answers for the seller, and UsageCounter.processCounted, with its period, for the process.

      fromBlock is required: a scan of a deployment starts at its FigaroDeploymentRecord.deploymentBlock. The node is asked for the two events only. A failed read throws, as every bulk reader of this SDK does (fetchLogsChunked): a partial scan would answer "nothing skipped" for the blocks it lost. A skipped batch whose BatchOperations log is absent from the node's answer, or whose stream does not decode, also throws: the verifier emits both in one transaction, so either is the node's error or a stream layout this SDK does not read, never a batch that carried nothing.
