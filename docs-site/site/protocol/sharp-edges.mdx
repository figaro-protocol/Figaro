Eight traps, in the order you can hit them: writing a clause spec, building a commit or a checkout, resolving a process and recording what it earned, then reading resolved state back. Each is a real mechanic verified against the shipped contracts and SDK. Where the canonical explanation lives in SDK source, this page links to it rather than restating it.

Read the [whole model](/) first, and [The contracts](/protocol/contracts/) for the surfaces these traps sit on.

## Spec-authoring — before you register

**Reserved `block.design.article` values, chosen by accident, are silent.** Two values are reserved and read straight off your spec: `"mandatory"` folds the clause into every agreement, and `"attestations"` makes the clause a runtime process log committed as an empty anchor. Each changes what the clause does at composition time; nothing warns you, nothing throws, and registration is permanent and first-write-wins — so if that is not what you mean, group under any other word before you register. What each one does is on [Clauses and agreements](/protocol/clauses/).

## Commit-time — building the struct you sign

**There is no incremental approval anywhere in `FigaroCore`.** Every `commit` — root or sub-order — pulls the FULL per-order bond (buyer `2 × payment`, seller `2 × cumulativeValue`), never the increment over bonds `FigaroCore` already holds from earlier orders. Approve only the increment and `commit` reverts inside the denomination with `ERC20InsufficientAllowance` (carried in `CORE_ABI`, so it decodes by name). Use `calculateSubOrderApproval`, never hand-roll the number; `assertApprovalCoversBond` throws before the transaction is sent rather than letting an under-approval surface as an opaque revert. Canonical: [`sdk/src/bonds.ts`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/bonds.ts).

**Compute `compositionHash` from the raw template, never from checkout-filled clauses.** Call `templateCompositionHash(template)` before any buyer, catalog, or pricing fill touches it. Compute it after merging those fills and you get a hash `AssemblyRegistry` never anchored — the provenance section is written mechanically from the template's own identity (`fillProvenanceSection`), and the hash cannot appear inside the composition it hashes. Canonical: [`sdk/src/checkoutPlan.ts`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/checkoutPlan.ts); what the composition hash covers is on [Clauses and agreements](/protocol/clauses/).

**A fee-on-transfer token makes `FigaroCore` refuse the commit.** The bond arithmetic depends on `FigaroCore` receiving exactly what was committed; a fee-on-transfer or rebasing ERC-20 breaks that, and `FigaroCore` reverts `FeeOnTransferDetected` (`src/core/kernel/FigaroCore.sol:134`). Pay in a plain, non-fee-on-transfer, non-rebasing token. See the error on [The contracts](/protocol/contracts/).

**A process cannot mix ERC-20s.** The 2:1 bond ratio is a same-unit comparison, so `FigaroCore` refuses any oracle or DEX dependency that would compare across tokens and reverts `CurrencyMismatch` on an extending order whose `currency` differs from the process's. Mix currencies by composing parallel processes, or swap before commit — never within one process. The cost model is on [Composition](/protocol/composition/).

## Resolution-time — resolving, and recording what it earned

**The id `resolveProcess` takes is not the id its structs carry.** The first argument is `FigaroCore`'s *derived* process id; every struct inside `commitments` must be the one the parties *signed* — and a root order signed `processId = 0`. Feed back the derived id that `OrderCommitted` carries — the natural move, since event reconstruction hands you exactly that — and `FigaroCore` recomputes an order hash matching no committed order, reverting `OrderNotCommitted`. `restoreSignedProcessId(c, chainId, core)` is the bridge: if treating a commitment as a root reproduces its own processId it WAS a root, so it is returned with `processId = 0`; otherwise it is a sub-order, returned unchanged. `orderToCommitment` gives you the derived-id form from an event; you must pass every element through `restoreSignedProcessId` before hashing or submitting. The SDK's `executeAction` applies it for you; a hand-rolled `cast` call does not. Canonical: [`sdk/src/commitments.ts`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/commitments.ts) and the [SDK manual](/building/sdk/).

**A closed accrual period does not throw — it returns a report with nothing recorded.** Usage must be recorded AT RESOLUTION or the designer credit is deniable later — a seller can unstake, a period can close, and a deferred count is permanently refusable. `recordClauseUsage` and `recordAssemblyUsage` each open by calling `UsageCounter.currentPeriod()`, which reverts `AccrualClosed()` once the last accrual period has ended (`src/build/rewards/UsageCounter.sol:398-403`). The SDK's `recordProcessUsage` never sends a leg the counter excludes (at the reference genesis the provenance clause alone; `figaro-commerce` and `figaro-topology` earn) and names it in the report's `excluded`; a leg it does send and that reverts lands in the report's `failures` array with nothing thrown, and the assembly leg is independent of the clause legs. The boundary is sharp long before the last period ends, too: a use counts in the period open *when you call*, not the one the process resolved in. Call `recordProcessUsage` in the same breath as the resolve, and read the report. Canonical: [`sdk/src/agent/autonomous.ts`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/agent/autonomous.ts).

## Read-time — after resolution

**`orderStatus == 0` means "not on this path," never "not resolved."** A batch-resolved process reads `core.orderStatus == 0` forever — the direct path and the [batch path](/protocol/scaling/) share no state, and there is no migration between them. Gate on `orderStatus` alone and batched trade is invisible to you, permanently. Fold both event streams — `OrderResolved`/`ProcessResolved` from `FigaroCore` and `BatchSettled` from `FigaroBatchVerifier` — never one alone. The full statement is on [Scaling](/protocol/scaling/) and the two-paths table on [The contracts](/protocol/contracts/).
