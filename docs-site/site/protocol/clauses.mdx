A clause is data — a JSON spec, registered publicly, that defines one term of an agreement. It is what a clause is in a paper contract, made verifiable: its content is a public document, identified by a hash over its own bytes and anchored on chain, so what a trade's terms say can be checked, not asserted.

Read the [whole model](/) first. Two of the six nouns live here and one seam runs through them: a **clause** is one relationship's term; an **agreement** is the clauses composed for one order, whose merkle root is the `checkoutHash` that offer and acceptance — the buyer's and seller's signatures — are taken over; a **registered agreement** is one order's clauses composed once, value-free, and registered so any assembly can reuse it; an **assembly** is registered agreements composed, one per agreement, into something anyone can reuse. Composition is permissionless: someone writes a term once and publishes it; anyone whose agreement needs it composes it in, and nobody asks permission either way.

Everything below is verified against the shipped SDK (`sdk/src/agreement.ts`, `sdk/src/discovery.ts`, `sdk/src/assembly.ts`, `sdk/src/clauses/`) and the registries; every hash is a pure function you can call with no chain.

## The five hashes, and exactly what each covers

Five different hashes are computed over what you write, and mixing them up is the most expensive authoring mistake — registration is permanent and first-write-wins.

**1. The clause key — a clause's identity and its content at once.** `keccak256` of exactly the bytes pinned at the clause's `contentURI`: the *whole* spec document — `clauseId`, `version`, `title`, `description`, `fields`, and *all* of `block`, editorial text included. The SDK pins the canonical JSON, `canonicalize(spec)` (sorted keys at every depth, array order kept, no whitespace), and `computeClauseKey(spec)` is `keccak256` of those bytes (`sdk/src/discovery.ts:66`; the same value as `canonicalContentHash(spec)`, `sdk/src/agreement.ts:188`). It is the key `ClauseRegistry` registers, every agreement clause's `clause`, the `clauseId` argument of the attest calls, and the key `FigaroBatchVerifier` checks every witness spec against. Change one label in `block` and you have a different key, which is a different clause, so pin exactly the bytes you hashed.

**2. The clause leaf — one clause's place in one agreement.** `keccak256(keccak256(clauseKey || hashClauseData))` (`sdk/src/agreement.ts:259`), where `clauseKey` is the clause key of (1) used verbatim (not re-hashed), and `hashClauseData = keccak256(canonicalJSON(clause.data))`. The inner hash binds the clause; the outer hash domain-separates leaves from internal nodes (a leaf preimage is 32 bytes, an internal node's is 64, so no node can be replayed as a leaf). This is the *only* thing the merkle tree — and the on-chain `clauseDataHash` argument to the attest calls and `recordClauseUsage` — needs, so a private clause's plaintext never has to be present to build or verify the tree.

**3. `checkoutHash` — an order's terms, what both parties sign.** The merkle root over an order's sorted clause leaves (`sdk/src/agreement.ts:302`). The checkout hash *is* the merkle root — there is no separate wrapper. It is the field of the same name in the `Commitment` struct, so the two signatures at commit are taken over exactly the set of clauses composed for that order. Any clause not in the tree cannot be attested against the order, and any clause in it is inclusion-provable on chain.

**4. `agreementHash` — a registered agreement's identity.** The merkle root over one leaf per composed clause, `keccak256(keccak256(clauseKey ‖ keccak256(fills)))` under the agreement format's leaf convention (`agreementHashOf(doc)`; a one-clause agreement's hash is its leaf, and `buildRegisteredClauseInclusionProof` proves a clause's membership): the clause keys composed for one agreement and the designer's fills, value-free, the topology clause composed with `{}`; the document's `name`, `summary` and `description` are excluded. It is `agreementHashOf(doc)`, and it is the key `AgreementRegistry` binds on. It is a design-time key: never confuse it with (3), the root of one filled order.

**5. `assemblyHash` — an assembly's identity.** A merkle root over the assembly's agreements, built with the assembly tree's own leaf convention, the leaf of (2) with `assemblyLeafDomain = keccak256("figaro-assembly-leaf")` mixed into the hash so that no agreement root opens an assembly leaf: one leaf per agreement keyed by its `agreementHash`, plus one leaf for the assembly-scoped clauses when any are composed; editorial prose excluded. It is `assemblyHashOf(assembly)`, and it is the key `AssemblyRegistry` binds on. Identical compositions collapse to one binding; renaming never forks identity.

```ts
import { computeClauseKey, computeCheckoutHash, agreementHashOf,
         assemblyHashOf } from "@figaro-protocol/sdk";

computeClauseKey(spec);              // (1) the clause key — keccak256 of canonicalize(spec), the bytes you pin
computeCheckoutHash(agreement);     // (3) the checkoutHash both parties sign
agreementHashOf(composed);            // (4) a registered agreement's agreementHash — its identity
assemblyHashOf(assembly);   // (5) an assembly's assemblyHash — the merkle root over its agreements
// (2) the clause leaf falls out of the agreement's merkle tree; inspect it with
//     buildSignedClauseInclusionProof(agreement, clauseKey)
```

## The clause-spec format

A spec lives off-chain as JSON at the `contentURI` its registration emits; its clause key is its integrity, checked by hashing the bytes fetched from that URI. The published definition of the format is the JSON Schema at [`sdk/src/clauses/clause-spec.schema.json`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/clauses/clause-spec.schema.json) — a closed subset of JSON Schema whose field `type` is one of `string`, `integer`, `bigint` (a decimal string), `boolean`, `enum`, `array`, `object`.

**The spec has two halves, and the protocol ends between them.**

- **Top level — the protocol:** the spec's own labels — `clauseId`, a name, and `version`, an integer lineage counter, both required by the schema and read by people, never by the chain or a leaf (`src/build/registries/ClauseRegistry.sol:16-18`) — `title`, `description`, and the content `fields`/`stages`. `fields` are stage-0, the committed content; `stages` keyed by the on-chain `uint8` stage are the shapes of *evidence* attested while the process is open (a temperature reading, measured grams). The SDK validates content against this off-chain; the bonds secure what was signed.
- **`block` — the presentation:** phase sections named for their reader — `design` (`article`, `scope`, `nestsUnder`, `fills`, `composes`), `checkout` (`catalogueFills`, `profileFills`), `runtime`. Nothing on-chain or in the SDK's content layer reads `block`.

`fields` are the protocol; everything in `block` is replaceable presentation. Anyone can build a different frontend — ignore `block`, invent their own — and still get the contracts, the mechanisms, the verified `fields`, and designer rewards. A surface driven by `block` is designed presentation of verified clauses; a hardcoded list or a stored role or category is drift.

Two `block.design.article` values are reserved and read straight off your spec: `"mandatory"` makes the clause one a designer never selects on its own: a registered agreement whose clauses all carry it is what a designer picks for every agreement of an assembly, and its clauses merge in (this is how `figaro-commerce` and `figaro-topology` reach every order), and `"attestations"` makes the clause a runtime process log committed as an empty anchor. Both behave differently than a plain group with no warning, and registration is permanent — so if that is not what you mean, group under any other word before you register.

Validate and encode generically — there is no per-clause code path:

```ts
import { parseClauseSpec, validateContent,
         encodeContentFromSpec } from "@figaro-protocol/sdk/clauses";

const spec = parseClauseSpec(json);          // validates against the published schema
validateContent(content, spec, { stage: 0 });// rejects unknown fields; applies the stage's field set
encodeContentFromSpec(content, spec);        // the one spec-driven encoder, any clause
```

Every consumer loads each spec live from `ClauseRegistry` → IPFS; nothing bundles a copy. A never-seen clause hashes, validates, and encodes the same way as any other.

## How an agreement composes from clauses

An agreement is the set of clauses composed for one order. Each `AgreementClause` is `{ clause, data }`: `clause` is the clause key and `data` the clause's content (or `dataHash`, its fingerprint, for a withheld clause; `sdk/src/agreement.ts:43-55`); the parties sort the leaves, build the merkle root, and sign it. That root is the `checkoutHash` in the `Commitment` — so signing the order *is* signing exactly the composed terms.

One clause is always the order's shape: `figaro-topology` states which seller follows which. It is committed at signing as a merkle leaf like every other clause, inclusion-provable against `checkoutHash` — `FigaroCore` stores no parent or child, so indexers read a process's topology from the signed agreement, never from the chain.

## How a registered agreement is composed and reused

A **agreement** is the clauses composed for one agreement, with the fills the designer gives them, and no values: `RegisteredAgreement { name?, summary?, description?, clauses }`, where `clauses` maps each clause key to the designer's fills. The topology clause is composed with `{}`: who follows whom belongs to the agreement, so one registered agreement can sit in any agreement of any assembly. Its key is `agreementHashOf(doc)` (hash 4 above).

Register it once and every designer can reuse it:

1. Compose the clauses, read live from `ClauseRegistry`; the mandatory clauses are written in, nothing picked (below).
2. Compute `agreementHash = agreementHashOf(doc)` and read `AgreementRegistry.bindings(agreementHash)`: a live binding means the agreement is already registered — bind it as is.
3. Otherwise pin the document and call `registerAgreement(agreementHash, contentURI)` with `value = registrationDeposit()` ([AgreementRegistry](/protocol/contracts/)).

**Hydration — verify by the key.** A reader that meets an `agreementHash` reads the binding's `contentURI`, fetches the document, parses it, and accepts it only if `agreementHashOf(doc)` equals the registered key: `anchorRegisteredAgreement(raw, agreementHash)` returns the agreement or `null`. The check is on the key, not the raw bytes, because the editorial fields sit outside the key. A failed fetch, a failed parse or a mismatch is absence: the agreement, and the assembly holding it, is not offered — never a fallback to a bundled or inline copy. A withdrawn stake leaves the binding readable, so assemblies already composed from it keep hydrating; a reader offers only live registrations for a new composition.

## How an assembly composes from registered agreements

An assembly is a merkle tree of agreements, one leaf per agreement, each a registered agreement, plus the clauses composed once for the whole assembly. It registers once, so anyone who fits the shape trades through it without drawing it again. The assembly is `{ name?, summary?, description?, faq?, assemblyClauses?, agreements: AssemblyAgreement[] }`, each `AssemblyAgreement` `{ id: "agreement-<i>", agreementHash, clauses }`, where the agreement's `clauses` hold the fills that belong to the position — the topology clause's `{ "follows": ["agreement-<j>", …] }`, naming the agreements it follows. The topology stays a clause: at design time in the assembly's agreement, at runtime in the signed agreement.

**The root.** `assemblyHash = assemblyHashOf(assembly)` is a merkle root with the assembly tree's own leaf convention, `keccak256(keccak256(assemblyLeafDomain ‖ key ‖ keccak256(bytes)))` with `assemblyLeafDomain = keccak256("figaro-assembly-leaf")`, sorted-pair hashing:

- one leaf per agreement `i` (0-based, assembly order): key the agreement's `agreementHash`; bytes the canonical JSON `{"clauses":{…},"slot":i}` (`agreementLeafBytes(slot, i)`; object keys sorted, arrays in assembly order);
- one **assembly terms leaf**, present only when `assemblyClauses` is non-empty: key `ASSEMBLY_TERMS_LEAF_KEY` = `keccak256("figaro-assembly-terms")`; bytes the canonical JSON of `assemblyClauses`.

A one-leaf tree's root is its leaf. Agreements are ordered, so one registered agreement may hold two. **Membership is proved, never looked up:** `buildAgreementInclusionProof(assembly, i)` returns the sorted-pair proof of agreement `i`'s leaf under `assemblyHash`, and `slotContentHash = keccak256(agreementLeafBytes(slot, i))`. `AssemblyRegistry` stores the root and a URI and checks nothing about the agreements inside it; `AgreementRegistry` knows no assembly.

**The mandatory clauses — written in, never picked.** An agreement is not an agreement without commerce and topology, so a canvas writes them into every agreement it registers before anything else is composed. Which clauses they are is read from `ClauseRegistry`: the DAO wallet's live registrations whose spec declares the `"mandatory"` article at agreement scope, one per shape, the later registration winning where two of one shape are live (`mandatoryClauses(rows, specs, registrant)`). Mandatory is a shape, never a name: commerce declares `payment`, `currency` and `lineItems` as content and topology declares `follows` (`specIsCommerceShape`, `specIsTopologyShape`); every reader finds them by those fields. Pass the set as `mandatory` to `buildAssembly` or `composeOrderAgreement`, which write it in first and refuse an agreement without one clause of each shape or with two; a registered agreement bound as is must carry both shapes itself, whatever their keys. A mandatory-article registration by any other wallet is an ordinary clause. In the protocol's clause set the two mandatory specs are `figaro-commerce` (payment and denomination) and `figaro-topology` (order shape), both agreement-scoped. Each earns for its designer of record like any other clause.

**The seeding order.** Clauses, then agreements, then the assembly: register each clause the agreements name, then each distinct agreement once (one stake each; skip a key already registered), then the assembly whose agreements name them.

The link from an order to the registered agreement and the assembly it instantiated is a leaf of the agreement format, not a clause: the **provenance leaf**. Its key is `PROVENANCE_LEAF_KEY`, `keccak256("figaro-agreement-provenance")` = `0x26dc18a2251a8f4629ada6df88b7c98553e011c08682d28ce5bb51a441227dc6` — the hash of a plain label, not of any spec's bytes; under keccak256's second-preimage resistance no spec has this key. `ClauseRegistry` and `AssemblyRegistry` take any bytes32, so a wallet can still register it there, and accrual refuses it — and the assembly terms key — whatever a registry holds: the direct path reverts (`ReservedKeyIsNotARegistration`, `src/build/rewards/UsageCounter.sol`), the guest refuses a batch usage claim keyed on either (`prover/lib/src/kernel.rs`), the counter's batch path skips both, and `AgreementRegistry` refuses both as registrations. An attestation on it is checked by the format's own rule, never as a clause (`prover/lib/src/kernel.rs:438`). Its committed bytes are the canonical JSON `{"agreementHash":"0x<64 lowercase hex>","assemblyHash":"0x<64 lowercase hex>"}` (`provenanceLeafBytes(agreementHash, assemblyHash)`; `decodeProvenanceContent(bytes)` reads them back, or returns `null`), and it enters the merkle tree as any clause leaf does, `keccak256(keccak256(key ‖ keccak256(bytes)))` (`computeProvenanceLeaf(agreementHash, assemblyHash)`). Checkout writes both keys from the agreement the order instantiates; an agreement with no `provenance` names no assembly and has no such leaf. `UsageCounter.recordAgreementUsage` reproduces those bytes from the two keys it is given and proves the leaf against `checkoutHash`, which is how a resolved process credits the registered agreement's designer; `recordAssemblyUsage` proves the same leaf and then the agreement's membership proof under `assemblyHash`, which is how it credits the assembly's designer ([UsageCounter](/protocol/contracts/)). While the process is open, the buyer can attest the leaf with `attestAsBuyer` (`@figaro-protocol/sdk/agent`); `provenanceLeafAttestation(agreement)` returns its inputs — the reserved key in the clause-key position, stage `0`, the inclusion proof, and the hash of the bytes as both `clauseDataHash` and `contentRef` — and the coordinator refuses any attestation once the order is resolved (`OrderResolved`, `src/core/attestation/AttestationCoordinator.sol:187`). That attestation is the public link from the process to its assembly: a reader computes `provenanceContentRef` for a registered agreement hash and composition and compares it to the attestation's `contentRef`, with no spec and no access to the agreement. The batch path accepts the same attestation with the bytes as its clause data and no spec (`validate_provenance_attestation`, `prover/lib/src/kernel.rs:361`).

The `assemblyHash` covers the composition and nothing else: a different registered agreement in the list, a re-wired topology, a different order of agreements, or different assembly-scoped terms all produce a different assembly — and a different clause set or one different design-filled value inside a agreement is a different `agreementHash`, so a different leaf; editorial prose (`name`, `summary`, `description`) is excluded, so renaming never forks it. The flip side of excluding prose: prose is not identity, so it does not protect a composition from being anchored by someone else first.

```ts
import { assemblyHashOf, deriveAssemblySlug } from "@figaro-protocol/sdk";

const h = assemblyHashOf(assembly);            // the registry key: the merkle root over the agreements
buildAgreementInclusionProof(assembly, 0);                   // the first agreement's membership proof under h
deriveAssemblySlug(h);                                  // "asm-<first 8 bytes>" — off-chain, never stored
assemblyHashOf({ ...assembly, name: "Anything" }) === h;  // true: prose is excluded
```

Compute the root from the *raw* assembly, before any buyer, catalog, or pricing fill touches it; compute it after merging those fills and you get a hash the registry never anchored.

## Document anchoring — the public/withheld seam

The chain holds fingerprints, never preimages, so each clause is anchored by its `hashClauseData` while its content lives off-chain on IPFS. A clause takes one of two forms, and the merkle leaf is identical either way:

- **Public** — the clause carries plaintext `data`, pinned as plaintext, and `hashClauseData` is computed from it. A reader fetches the bytes, hashes them back, and decodes against the spec.
- **Withheld** — the clause carries a `dataHash` fingerprint in place of `data` (paid-edge or private content), pinned encrypted. It contributes the exact same leaf, so the agreement root is unchanged — a party can publish or verify the agreement's structure while keeping the plaintext off every public surface.

**A clause carries `data` XOR `dataHash`, never both.** The hashing function refuses a clause with both, at the hashing locus, so no consumer — leaf, root, or the sign gate — can pass a clause that signs one thing and shows another (`sdk/src/agreement.ts:221-236`). Per-field disposition (`"public"` default, or `"private"`) is declared in the spec and governs publication and grain policy; the chain carries only the clause data hash either way. Withholding is fail-closed: an unknown spec, or any private field in the encoded set, publishes nothing, and a lookup that resolves empty reads as absence.

## Registration — permissionless, first-write-wins, ETH-staked

A new clause is a spec plus a registration, nothing else — no validator contract, no interface step; the proof engine is generic and takes the spec as a witness input anchored by the registered clause key.

```solidity
function registerClause(bytes32 clauseKey, string calldata contentURI)
    external payable;   // ClauseRegistry — first-write-wins on the key, immutable, under a stake
```

The key is `computeClauseKey(spec)`, `keccak256` of the canonical bytes you pin at `contentURI` (`src/build/registries/ClauseRegistry.sol:146-150`). The registry stores no name, no version and no separate content hash: the key is the content hash. It takes the key as given and never sees the bytes, so a key whose bytes nobody can fetch is a registration no reader can verify (`:49-51`). Registration anchors identity and integrity only — no group field (grouping is `block.design.article`, off-chain), no reward tag (designer rewards are uniform on real use), no validator (a registered clause is immediately attestable and batch-resolvable). The stake is a deploy-time parameter: read `registrationDeposit()` live and send exactly it. `clauseId` and `version` are the spec's own labels: two specs that carry the same name are two clauses with two keys, a revision of a clause is a new spec with a new key registered beside the old one, and compatibility between two revisions, if it ever matters, is derived by diffing two immutable specs.

```ts
import { canonicalize, computeClauseKey, anchorClauseSpec } from "@figaro-protocol/sdk";

const bytes = canonicalize(spec);          // the whole raw document, block included: the bytes to pin
const clauseKey = computeClauseKey(spec);  // keccak256 of exactly those bytes
// read registered(clauseKey) first (same bytes, same clause), pin `bytes`,
// then registerClause(clauseKey, contentURI) with value = registrationDeposit()

// A reader verifies a fetched spec by hashing the bytes it fetched:
anchorClauseSpec(fetchedBytes, clauseKey); // the parsed spec, or null when keccak256(bytes) != clauseKey
```

`anchorClauseSpec` re-canonicalizes nothing (`sdk/src/anchored.ts:63`): a spec pinned in any other byte form — pretty-printed, keys re-ordered — has a different key and never verifies against the one you registered ([Sharp edges](/protocol/sharp-edges/)).

Withdrawing the stake de-surfaces the clause for new compositions but never deletes the binding: orders already committed against it still resolve. Agreements register the same way on `AgreementRegistry` (keyed by `agreementHash`) and assemblies on `AssemblyRegistry` (keyed by `assemblyHash`), with the same permanence.

**One spec, two enforcement layers, in lockstep.** Off-chain, the SDK's `parseClauseSpec` and `validateContent` gate every signature. On the batch path, that same spec drives an in-proof content check: a generic SP1 engine validates each clause's content against its spec (supplied as a witness) after checking that `keccak256` of the spec's bytes is the clause key the clause names (`prover/lib/src/kernel.rs:456-458`), and `FigaroBatchVerifier` resolves the batch only if each spec binding carries that key in both words and `ClauseRegistry.registered(key)` is true (`src/core/verifier/FigaroBatchVerifier.sol:546-555`). The engine's verification key covers the *engine*, not a clause list, so a never-seen clause resolves through the proven path with zero code changes. There are no per-clause validator contracts, by design — a clause is data, not code.

The contract surfaces these calls belong to — `ClauseRegistry`, `AgreementRegistry`, `AssemblyRegistry`, `AttestationCoordinator`, `UsageCounter`, `FigaroBatchVerifier` — are on [The contracts](/protocol/contracts/); the reward that follows real use is on [Designer rewards](/token/designer-rewards/).
