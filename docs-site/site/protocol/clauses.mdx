A clause is data — a JSON spec, registered publicly, that defines one term of an agreement. It is what a clause is in a paper contract, made verifiable: its content is a public document, identified by a hash over its own bytes and anchored on chain, so what a trade's terms say can be checked, not asserted.

Read the [whole model](/) first. Two of the six nouns live here and one seam runs through them: a **clause** is one relationship's term; an **agreement** is the clauses composed for one order, whose merkle root is the `agreementHash` that offer and acceptance — the buyer's and seller's signatures — are taken over; an **assembly** is agreements composed into something anyone can reuse. Composition is permissionless: someone writes a term once and publishes it; anyone whose agreement needs it composes it in, and nobody asks permission either way.

Everything below is verified against the shipped SDK (`sdk/src/agreement.ts`, `sdk/src/discovery.ts`, `sdk/src/assembly.ts`, `sdk/src/clauses/`) and the registries; every hash is a pure function you can call with no chain.

## The four hashes, and exactly what each covers

Four different hashes are computed over what you write, and mixing them up is the most expensive authoring mistake — registration is permanent and first-write-wins.

**1. The clause key — a clause's identity and its content at once.** `keccak256` of exactly the bytes pinned at the clause's `contentURI`: the *whole* spec document — `clauseId`, `version`, `title`, `description`, `fields`, and *all* of `block`, editorial text included. The SDK pins the canonical JSON, `canonicalize(spec)` (sorted keys at every depth, array order kept, no whitespace), and `computeClauseKey(spec)` is `keccak256` of those bytes (`sdk/src/discovery.ts:60`; the same value as `canonicalContentHash(spec)`, `sdk/src/agreement.ts:164`). It is the key `ClauseRegistry` registers, every agreement section's `clause`, the `clauseId` argument of the attest calls, and the key `FigaroBatchVerifier` checks every witness spec against. Change one label in `block` and you have a different key, which is a different clause, so pin exactly the bytes you hashed.

**2. The section leaf — one clause's place in one agreement.** `keccak256(keccak256(clauseKey || sectionDataHash))` (`sdk/src/agreement.ts:235`), where `clauseKey` is the clause key of (1) used verbatim (not re-hashed), and `sectionDataHash = keccak256(canonicalJSON(section.data))`. The inner hash binds the section; the outer hash domain-separates leaves from internal nodes (a leaf preimage is 32 bytes, an internal node's is 64, so no node can be replayed as a leaf). This is the *only* thing the merkle tree — and the on-chain `sectionHash` argument to the attest calls and `recordClauseUsage` — needs, so a private section's plaintext never has to be present to build or verify the tree.

**3. `agreementHash` — an order's terms, what both parties sign.** The merkle root over an order's sorted section leaves (`sdk/src/agreement.ts:268`). The agreement hash *is* the merkle root — there is no separate wrapper. It is the field of the same name in the `Commitment` struct, so the two signatures at commit are taken over exactly the set of clause sections composed for that order. Any clause not in the tree cannot be attested against the order, and any clause in it is inclusion-provable on chain.

**4. `compositionHash` — an assembly's identity.** keccak256 over the canonical *composition subset* of an assembly template — its composed agreements (their clauses, values, and topology), plus assembly-scoped clauses when any are composed; editorial prose excluded. It is `templateCompositionHash(template)` (`sdk/src/assembly.ts:104`), and it is the key `AssemblyRegistry` binds on. Identical compositions collapse to one binding; renaming never forks identity.

```ts
import { computeClauseKey, computeAgreementHash,
         templateCompositionHash } from "@figaro-protocol/sdk";

computeClauseKey(spec);              // (1) the clause key — keccak256 of canonicalize(spec), the bytes you pin
computeAgreementHash(agreement);     // (3) the agreementHash both parties sign
templateCompositionHash(template);   // (4) an assembly's compositionHash — its identity
// (2) the section leaf falls out of the agreement's merkle tree; inspect it with
//     buildSectionInclusionProof(agreement, clauseKey)
```

## The clause-spec format

A spec lives off-chain as JSON at the `contentURI` its registration emits; its clause key is its integrity, checked by hashing the bytes fetched from that URI. The published definition of the format is the JSON Schema at [`sdk/src/clauses/clause-spec.schema.json`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/clauses/clause-spec.schema.json) — a closed subset of JSON Schema whose field `type` is one of `string`, `integer`, `bigint` (a decimal string), `boolean`, `enum`, `array`, `object`.

**The spec has two halves, and the protocol ends between them.**

- **Top level — the protocol:** the spec's own labels — `clauseId`, a name, and `version`, an integer lineage counter, both required by the schema and read by people, never by the chain or a leaf (`src/build/registries/ClauseRegistry.sol:16-18`) — `title`, `description`, and the content `fields`/`stages`. `fields` are stage-0, the committed content; `stages` keyed by the on-chain `uint8` stage are the shapes of *evidence* attested while the process is open (a temperature reading, measured grams). The SDK validates content against this off-chain; the bonds secure what was signed.
- **`block` — the presentation:** phase sections named for their reader — `design` (`article`, `scope`, `nestsUnder`, `fills`, `composes`), `checkout` (`catalogueFills`, `profileFills`), `runtime`. Nothing on-chain or in the SDK's content layer reads `block`.

`fields` are the protocol; everything in `block` is replaceable presentation. Anyone can build a different frontend — ignore `block`, invent their own — and still get the contracts, the mechanisms, the verified `fields`, and designer rewards. A surface driven by `block` is designed presentation of verified clauses; a hardcoded list or a stored role or category is drift.

Two `block.design.article` values are reserved and read straight off your spec: `"mandatory"` folds the clause into every agreement (this is how `figaro-commerce` and `figaro-topology` ride along), and `"attestations"` makes the clause a runtime process log committed as an empty anchor. Both behave differently than a plain group with no warning, and registration is permanent — so if that is not what you mean, group under any other word before you register.

Validate and encode generically — there is no per-clause code path:

```ts
import { parseClauseSpec, validateContent,
         encodeContentFromSpec } from "@figaro-protocol/sdk/clauses";

const spec = parseClauseSpec(json);          // validates against the published schema
validateContent(content, spec, { stage: 0 });// rejects unknown fields; applies the stage's field set
encodeContentFromSpec(content, spec);        // the one spec-driven encoder, any clause
```

Every consumer loads each spec live from `ClauseRegistry` → IPFS; nothing bundles a copy. A never-seen clause hashes, validates, and encodes the same way as any other.

## How an agreement composes from clauses

An agreement is the set of clause sections composed for one order. Each `AgreementSection` is `{ clause, data }`: `clause` is the clause key and `data` the clause's content (or `dataHash`, its fingerprint, for a withheld section; `sdk/src/agreement.ts:43-56`); the parties sort the leaves, build the merkle root, and sign it. That root is the `agreementHash` in the `Commitment` — so signing the order *is* signing exactly the composed terms.

One clause is always the order's shape: `figaro-topology` states which seller follows which. It is committed at signing as a merkle leaf like every other section, inclusion-provable against `agreementHash` — `FigaroCore` stores no parent or child, so indexers read a process's topology from the signed agreement, never from the chain.

## How an assembly composes from agreements

An assembly is a composition template: it wires per-order agreements into a multi-order process and registers once, so anyone who fits the shape trades through it without drawing it again. A designer spawns sub-orders from any node and attaches the clauses that define each edge; those clauses are read live from `ClauseRegistry`, never a fixed menu.

Every agreement folds in the clauses whose spec declares the `"mandatory"` article. `buildAssemblyTemplate` folds every mandatory spec its `SpecSource` lists, with no selection among them, since two specs are two clauses; each folds at the level its scope names (`sdk/src/projection.ts:704-718`). Liveness comes from the source, not the fold: for a new composition, pass a source of the registrations whose stake is live. The fold set is the source you pass: a registration marking `"mandatory"` folds when your source lists it, whoever registered it, and every folded clause is in the template, where a review shows it before you anchor. In the protocol's clause set the two mandatory specs are `figaro-commerce` (payment and denomination) and `figaro-topology` (order shape), both agreement-scoped. Each earns for its designer of record like any other clause.

The link from an order to the assembly it instantiated is a leaf of the agreement format, not a clause: the **provenance leaf**. Its key is `PROVENANCE_LEAF_KEY`, `keccak256("figaro-agreement-provenance")` = `0x26dc18a2251a8f4629ada6df88b7c98553e011c08682d28ce5bb51a441227dc6` — the hash of a plain label, not of any spec's bytes; under keccak256's second-preimage resistance no spec has this key. A registry takes any bytes32, so a wallet can still register it, and accrual refuses it whatever a registry holds: the direct path reverts `ProvenanceLeafIsNotARegistration` (`src/build/rewards/UsageCounter.sol:657`), the guest refuses a batch usage claim keyed on it (`prover/lib/src/kernel.rs:742-744`), and the counter's batch path skips it (`UsageCounter.sol:604`). An attestation on it is checked by the format's own rule, never as a clause (`prover/lib/src/kernel.rs:418`). Its committed bytes are `{"compositionHash":"0x<64 lowercase hex>"}` (`provenanceSectionBytes`), and it enters the merkle tree as any section leaf does, `keccak256(keccak256(key ‖ keccak256(bytes)))` (`sdk/src/agreement.ts:100-102`). Instantiating a template writes the template's own `compositionHash` into `agreement.provenance` on every order it realizes; an agreement with no `provenance` names no assembly and has no such leaf. `UsageCounter.recordAssemblyUsage` reproduces those bytes from the `compositionHash` it is given and proves the leaf against `agreementHash`, which is how a resolved process credits the assembly's designer ([UsageCounter](/protocol/contracts/)). While the process is open, the buyer can attest the leaf with `attestAsBuyer` (`@figaro-protocol/sdk/agent`); `provenanceLeafAttestation(agreement)` returns its inputs — the reserved key in the clause-key slot, stage `0`, the inclusion proof, and the hash of the bytes as both `sectionHash` and `contentRef` — and the coordinator refuses any attestation once the order is resolved (`OrderResolved`, `src/core/attestation/AttestationCoordinator.sol:199`). That attestation is the public link from the process to its assembly: a reader computes `provenanceContentRef(compositionHash)` for a registered composition and compares it to the attestation's `contentRef`, with no spec and no access to the agreement. The batch path accepts the same attestation with the bytes as its section data and no spec (`validate_provenance_attestation`, `prover/lib/src/kernel.rs:344`).

The `compositionHash` covers the composition and nothing else: a different clause set, one different design-filled value, a re-wired topology, or a different clause key (another spec, however close its text) all produce a different assembly; editorial prose (`name`, `summary`, `description`) is excluded, so renaming never forks it. The flip side of excluding prose: prose is not identity, so it does not protect a composition from being anchored by someone else first.

```ts
import { templateCompositionHash, deriveAssemblySlug } from "@figaro-protocol/sdk";

const h = templateCompositionHash(template);            // the registry key
deriveAssemblySlug(h);                                  // "asm-<first 8 bytes>" — off-chain, never stored
templateCompositionHash({ ...template, name: "Anything" }) === h;  // true: prose is excluded
```

Compute the hash from the *raw* template, before any buyer, catalog, or pricing fill touches it; compute it after merging those fills and you get a hash the registry never anchored.

## Document anchoring — the public/withheld seam

The chain holds fingerprints, never preimages, so each clause section is anchored by its `sectionDataHash` while its content lives off-chain on IPFS. A section takes one of two forms, and the merkle leaf is identical either way:

- **Public** — the section carries plaintext `data`, pinned as plaintext, and `sectionDataHash` is computed from it. A reader fetches the bytes, hashes them back, and decodes against the spec.
- **Withheld** — the section carries a `dataHash` fingerprint in place of `data` (paid-edge or private content), pinned encrypted. It contributes the exact same leaf, so the agreement root is unchanged — a party can publish or verify the agreement's structure while keeping the plaintext off every public surface.

**A section carries `data` XOR `dataHash`, never both.** The hashing function refuses a section with both, at the hashing locus, so no consumer — leaf, root, or the sign gate — can pass a section that signs one thing and shows another (`sdk/src/agreement.ts:133-144`). Per-field disposition (`"public"` default, or `"private"`) is declared in the spec and governs publication and grain policy; the chain carries only the section hash either way. Withholding is fail-closed: an unknown spec, or any private field in the encoded set, publishes nothing, and a lookup that resolves empty reads as absence.

## Registration — permissionless, first-write-wins, ETH-staked

A new clause is a spec plus a registration, nothing else — no validator contract, no interface step; the proof engine is generic and takes the spec as a witness input anchored by the registered clause key.

```solidity
function registerClause(bytes32 clauseKey, string calldata contentURI)
    external payable;   // ClauseRegistry — first-write-wins on the key, immutable, under a stake
```

The key is `computeClauseKey(spec)`, `keccak256` of the canonical bytes you pin at `contentURI` (`src/build/registries/ClauseRegistry.sol:146-150`). The registry stores no name, no version and no separate content hash: the key is the content hash. It takes the key as given and never sees the bytes, so a key whose bytes nobody can fetch is a registration no reader can verify (`:49-51`). Registration anchors identity and integrity only — no group field (grouping is `block.design.article`, off-chain), no reward tag (designer rewards are uniform on real use), no validator (a registered clause is immediately attestable and batch-resolvable). The stake is a deploy-time parameter: read `registrationDeposit()` live and send exactly it. `clauseId` and `version` are the spec's own labels: two specs that carry the same name are two clauses with two keys, a revision of a clause is a new spec with a new key registered beside the old one, and compatibility between two revisions, if it ever matters, is derived by diffing two immutable specs.

```ts
import { canonicalize, computeClauseKey, anchorClauseSpec } from "@figaro-protocol/sdk";

const bytes = canonicalize(spec);          // the whole raw document, block included: the bytes to pin
const clauseKey = computeClauseKey(spec);  // keccak256 of exactly those bytes
// read registered(clauseKey) first (same bytes, same clause), pin `bytes`,
// then registerClause(clauseKey, contentURI) with value = registrationDeposit()

// A reader verifies a fetched spec by hashing the bytes it fetched:
anchorClauseSpec(fetchedBytes, clauseKey); // the parsed spec, or null when keccak256(bytes) != clauseKey
```

`anchorClauseSpec` re-canonicalizes nothing (`sdk/src/anchored.ts:54`): a spec pinned in any other byte form — pretty-printed, keys re-ordered — has a different key and never verifies against the one you registered ([Sharp edges](/protocol/sharp-edges/)).

Withdrawing the stake de-surfaces the clause for new compositions but never deletes the binding: orders already committed against it still resolve. Assemblies register the same way on `AssemblyRegistry` (keyed by `compositionHash`), with the same permanence.

**One spec, two enforcement layers, in lockstep.** Off-chain, the SDK's `parseClauseSpec` and `validateContent` gate every signature. On the batch path, that same spec drives an in-proof content check: a generic SP1 engine validates each clause's content against its spec (supplied as a witness) after checking that `keccak256` of the spec's bytes is the clause key the section names (`prover/lib/src/kernel.rs:423-439`), and `FigaroBatchVerifier` resolves the batch only if each spec binding carries that key in both words and `ClauseRegistry.registered(key)` is true (`src/core/verifier/FigaroBatchVerifier.sol:546-555`). The engine's verification key covers the *engine*, not a clause list, so a never-seen clause resolves through the proven path with zero code changes. There are no per-clause validator contracts, by design — a clause is data, not code.

The contract surfaces these calls belong to — `ClauseRegistry`, `AssemblyRegistry`, `AttestationCoordinator`, `UsageCounter`, `FigaroBatchVerifier` — are on [The contracts](/protocol/contracts/); the reward that follows real use is on [Designer rewards](/token/designer-rewards/).
