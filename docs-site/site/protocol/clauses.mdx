A clause is data — a JSON spec, registered publicly, that defines one term of an agreement. It is what a clause is in a paper contract, made verifiable: its content is a public document, identified by a hash over its own bytes and anchored on chain, so what a trade's terms say can be checked, not asserted.

Read the [whole model](/) first. Two of the six nouns live here and one seam runs through them: a **clause** is one relationship's term; an **agreement** is the clauses composed for one order, whose merkle root is the `checkoutHash` that offer and acceptance — the buyer's and seller's signatures — are taken over; a **registered agreement** is one order's clauses composed once, value-free, and registered so any assembly can reuse it; an **assembly** is registered agreements composed, one per agreement, into something anyone can reuse. Composition is permissionless: someone writes a term once and publishes it; anyone whose agreement needs it composes it in, and nobody asks permission either way.

Everything below is verified against the shipped SDK (`sdk/src/agreement.ts`, `sdk/src/discovery.ts`, `sdk/src/assembly.ts`, `sdk/src/clauses/`) and the registries; every hash is a pure function you can call with no chain.

## The five hashes, and exactly what each covers

Five different hashes are computed over what you write, and mixing them up is the most expensive authoring mistake — registration is permanent and first-write-wins.

**1. The clause key — a clause's identity and its content at once.** `keccak256` of the canonical JSON of the spec *without its top-level `block`*: `clauseId`, `version`, `title`, `description`, `fields`, `stages` and every other top-level attribute, and none of `block`, which is presentation. Canonical means `canonicalize`: ECMAScript's `JSON.stringify` with no whitespace over objects whose keys are sorted, array order kept. A tool that does not use the SDK reproduces it exactly: array-index keys (`"2"`, `"10"`) first in numeric order, every other key by UTF-16 code unit, numbers as ECMAScript prints them (`1e+21`; no integer above 2^53), strings escaped as `JSON.stringify` escapes them with non-ASCII left raw, and no key named `__proto__`, `constructor` or `prototype`, which every reader strips, so `computeClauseKey` throws on a spec that carries one outside `block`. A generic sorted-keys serializer yields another key for a spec with ten or more numbered entries; `clauseKeyPreimage(spec)` returns those bytes and `computeClauseKey(spec)` is their `keccak256` (`sdk/src/discovery.ts:89`, `:102`). It is the key `ClauseRegistry` registers, every agreement clause's `clause`, the `clauseId` argument of the attest calls, and the key `FigaroBatchVerifier` checks every witness spec against. Change a label in `block` and the key stays; change a field, a stage or the title and you have a different key, which is a different clause. The SDK pins `canonicalize(spec)`, `block` included, so a reader gets the presentation with the spec.

**2. The clause leaf — one clause's place in one agreement.** `keccak256(keccak256(clauseKey || hashClauseData))` (`sdk/src/agreement.ts:259`), where `clauseKey` is the clause key of (1) used verbatim (not re-hashed), and `hashClauseData = keccak256(canonicalJSON(clause.data))`. The inner hash binds the clause; the outer hash domain-separates leaves from internal nodes (a leaf preimage is 32 bytes, an internal node's is 64, so no node can be replayed as a leaf). This is the *only* thing the merkle tree — and the on-chain `clauseDataHash` argument to the attest calls and `recordClauseUsage` — needs, so a private clause's plaintext never has to be present to build or verify the tree.

**3. `checkoutHash` — an order's terms, what both parties sign.** The merkle root over an order's sorted clause leaves (`sdk/src/agreement.ts:302`). The checkout hash *is* the merkle root — there is no separate wrapper. It is the field of the same name in the `Commitment` struct, so the two signatures at commit are taken over exactly the set of clauses composed for that order. Any clause not in the tree cannot be attested against the order, and any clause in it is inclusion-provable on chain.

**4. `agreementHash` — a registered agreement's identity.** The merkle root over one leaf per composed clause, `keccak256(keccak256(clauseKey ‖ keccak256(fills)))` under the agreement format's leaf convention (`agreementHashOf(doc)`; a one-clause agreement's hash is its leaf, and `buildRegisteredClauseInclusionProof` proves a clause's membership): the clause keys the agreement composes and the designer's fills, value-free, with no topology; the document's `name`, `summary` and `description` are excluded. It is `agreementHashOf(doc)`, and it is the key `AgreementRegistry` binds on. It is a design-time key: never confuse it with (3), the root of one filled order.

**5. `processDesignHash` — an assembly's identity.** A merkle root over the assembly's agreements, built with the assembly tree's own leaf convention, the leaf of (2) with `processLeafDomain = keccak256("figaro-assembly-leaf")` mixed into the hash so that no agreement root opens an assembly leaf: one leaf per agreement keyed by its `agreementHash`, plus one leaf for the assembly-scoped clauses when any are composed; editorial prose excluded. It is `processDesignHashOf(assembly)`, and it is the key `ProcessRegistry` binds on. Identical compositions collapse to one binding; renaming never forks identity.

```ts
import { computeClauseKey, computeCheckoutHash, agreementHashOf,
         processDesignHashOf } from "@figaro-protocol/sdk";

computeClauseKey(spec);              // (1) the clause key — keccak256 of the canonical spec without its block
computeCheckoutHash(agreement);     // (3) the checkoutHash both parties sign
agreementHashOf(composed);            // (4) a registered agreement's agreementHash — its identity
processDesignHashOf(assembly);   // (5) an assembly's processDesignHash — the merkle root over its agreements
// (2) the clause leaf falls out of the agreement's merkle tree; inspect it with
//     buildSignedClauseInclusionProof(agreement, clauseKey)
```

## The clause-spec format

A spec lives off-chain as JSON at the `contentURI` its registration emits; its clause key is its integrity, checked by parsing the document fetched from that URI, dropping its top-level `block`, canonicalizing and hashing. The published definition of the format is the JSON Schema at [`sdk/src/clauses/clause-spec.schema.json`](https://github.com/figaro-protocol/Figaro/blob/main/sdk/src/clauses/clause-spec.schema.json) — a closed subset of JSON Schema whose field `type` is one of `string`, `integer`, `bigint` (a decimal string), `boolean`, `enum`, `array`, `object`. An `enum` field names at most 256 values, since a value encodes as its `uint8` position; a spec with more does not parse in the SDK, and the published format states the same bound (`values`, `maxItems: 256`).

**The spec has two halves, and the protocol ends between them.**

- **Top level — the protocol:** the spec's own labels — `clauseId`, a name, and `version`, an integer lineage counter, both required by the clause-spec format and read by people, never by the chain or a leaf (`src/registries/ClauseRegistry.sol:16-18`) — `title`, `description`, and the content `fields`/`stages`. `fields` are stage-0, the committed content; `stages` keyed by the on-chain `uint8` stage are the shapes of *evidence* attested while the process is open (a temperature reading, measured grams). A `stages` key is the decimal of the stage, from `"0"` to `"255"`: digits only, with no sign, no leading zero and no whitespace. A spec with any other key (`"01"`, `"+1"`, `" 1"`, `"1.0"`) does not parse in the SDK (`stageOfKey`, `sdk/src/clauses/spec.ts`), and the published format's `stages` admits no other key. A `"0"` key sets the fields that content attested at stage 0 is encoded and validated over; the committed content is validated over `fields`. A signer's tool validates content against this before signing (the SDK is one such tool); the bonds secure what was signed.
- **`block` — the presentation:** phase sections, each named for the phase whose actor it instructs — `design`, the designer (`article`, `scope`, `nestsUnder`, `fills`, `composes`); `checkout`, the seller binding and the buyer filling and signing (`catalogueFills`, `profileFills`, `catalogueMeasures`, `pricedLines`, `derives`, `timeWindow`, `endpoints`, `registerLink`, `dataSources`, `heldValues`, `compositionFields`); `runtime`, the parties after commit (`interaction`, `modality`, `jurisdiction`, `documentPart`, `ladder`, `contentDigest`). A later phase may read an earlier section; no phase reads a section named for a later one. Nothing on-chain or in the SDK's content layer reads `block`.

`fields` are the protocol; everything in `block` is replaceable presentation. Anyone can build a different frontend — ignore `block`, invent their own — and still get the contracts, the mechanisms, the verified `fields`, and designer rewards. A surface driven by `block` is designed presentation of verified clauses; a hardcoded list or a stored role or category is drift.

Four `block.design.article` values are routed on by the reference frontend, read straight off your spec. `"attestations"` makes it present the clause as a runtime process log. What the parties sign for a clause is never read from its article: a spec that declares `"emptyAnchor": true` at its top level signs the empty anchor `{}`, whatever its article, and every other spec signs content validated over its `fields`. Three more are read by name: `"consent"` makes the frontend's agreement review, shown before signing, list the clause's values under a consent notice; `"denomination"` on an assembly-scoped clause has its unfilled designer-filled `address-hex` fields set to the deployment's token at seeding (`fillDeployTimeCurrency`); and `"dispute-resolution"` makes the frontend's audit view read the clause as the process's named forum. Each behaves differently than a plain group with no warning, and registration is permanent — so if that is not what you mean, group under any other word before you register. Any other word is a group heading only: the reference frontend groups the clause under it and composes it like any clause.

Validate and encode generically — there is no per-clause code path:

```ts
import { parseClauseSpec, validateContent,
         encodeContentFromSpec } from "@figaro-protocol/sdk/clauses";

const spec = parseClauseSpec(json);          // validates against the published schema
validateContent(content, spec, { stage: 0 });// rejects unknown fields; applies the stage's field set
encodeContentFromSpec(content, spec);        // the one spec-driven encoder, any clause
```

Every consumer loads each spec live from `ClauseRegistry` → IPFS; nothing bundles a copy. A never-seen clause hashes, validates, and encodes the same way as any other.

## How an agreement composes from clauses

An agreement is the set of clauses composed for one order. Each `AgreementClause` is `{ clause, data }`: `clause` is the clause key and `data` the clause's content (or `dataHash`, its fingerprint, for a withheld clause; `sdk/src/agreement.ts:43-55`); the parties sort the leaves, build the merkle root, and sign it. That root is the `checkoutHash` in the `Commitment` — so signing the order *is* signing exactly the composed terms.

Which order follows which is no clause: it is the agreement format's **topology leaf**, `Agreement.follows`, the order hashes of the orders this order follows, `[]` for the root of its process. Its committed bytes are the canonical JSON `{"follows":["0x<64 lowercase hex>",…]}` in the order given (`topologyLeafBytes(follows)`); its leaf is `keccak256(keccak256(TOPOLOGY_LEAF_DOMAIN ‖ uint256(n) ‖ keccak256(bytes)))`, with `TOPOLOGY_LEAF_DOMAIN = keccak256("figaro-agreement-topology")` = `0xbb19ab0597c6d28223160cd73f765e7ab09fb47de53be100cb982aec5ebc63af` and `n` the number of edges as a 32-byte big-endian word (`computeTopologyLeaf(follows)`). That inner preimage is 96 bytes, where a clause leaf's is 64, so no clause key opens it: nothing registers it, attests it or counts it. An assembly leaf's inner preimage is also 96 bytes (domain, key, data hash), and it is kept apart from the topology leaf by its first word, the domain: `PROCESS_LEAF_DOMAIN = keccak256("figaro-assembly-leaf")` = `0xb44cab2cf6dbf97cfe57060c8f30ee31552bc93f52859b4f32bd145f2882dfc6`, against `TOPOLOGY_LEAF_DOMAIN`. Checkout writes it from the assembly entry's `follows`, each label mapped to that entry's order hash; every agreement built from a design carries it, an empty list included, and one built without a design may leave it absent. The sign gate refuses a design-built agreement without it, any topology whose edges are not distinct 32-byte hashes, and a leaf that names another number of orders than the design entry it matches follows entries. Which orders the edges name is not checked: an order hash depends on that order's parties, payment and salt, which no design carries. `FigaroCore` stores no parent or child, so indexers read a process's topology from the signed agreement, never from the chain.

**The tree.** `checkoutHash` is the merkle root over every leaf of the agreement: one per clause (an agreement naming one clause key twice is refused), the provenance leaf when it names a design, and the topology leaf when it carries `follows`. A tool without the SDK rebuilds the root by these rules (`sortLeaves`, `hashPair` and `buildMerkleRoot` in `sdk/src/agreement.ts`):

- the leaves are sorted in ascending order of their 32-byte values read as unsigned integers (the SDK compares their lowercase hex, which gives the same order);
- each layer pairs its nodes left to right, the first with the second, the third with the fourth, and so on, and a pair hashes as `keccak256(min(a,b) ‖ max(a,b))`, the smaller value first, a 64-byte preimage;
- a node left without a partner at the end of a layer goes up to the next layer unchanged; it is never hashed with itself;
- the root is the one node left: a one-leaf tree's root is its leaf, and an empty tree's is `bytes32(0)`.

An assembly's root (`processDesignHashOf`) is built by the same rules over the assembly tree's leaves.

## How a registered agreement is composed and reused

A **registered agreement** is the design of an agreement: a merkle tree of clauses, one leaf per composed clause with the fills the designer gives it, and no values — `RegisteredAgreement { name?, summary?, description?, clauses }`, where `clauses` maps each clause key to the designer's fills. It carries no topology: who follows whom is set by each assembly that places the agreement (`ProcessDesignAgreement.follows`, `sdk/src/assembly.ts`), so one registered agreement can sit at any position of any assembly. It composes at least one clause: an empty one's key is `bytes32(0)`, which `AgreementRegistry.registerAgreement` refuses. Its key is `agreementHashOf(doc)` (hash 4 above).

Register it once and every designer can reuse it:

1. Compose the clauses, read live from `ClauseRegistry`; the agreement carries exactly the clauses composed (below).
2. Compute `agreementHash = agreementHashOf(doc)` and read `AgreementRegistry.bindings(agreementHash)`: a live binding means the agreement is already registered — bind it as is.
3. Otherwise pin the document and call `registerAgreement(agreementHash, contentURI)` with `value = registrationDeposit()` ([AgreementRegistry](/protocol/contracts/)).

**Hydration — verify by the key.** A reader that meets an `agreementHash` reads the binding's `contentURI`, fetches the document, parses it, and accepts it only if `agreementHashOf(doc)` equals the registered key: `anchorRegisteredAgreement(raw, agreementHash)` returns the agreement or `null`. The check is on the key, not the raw bytes, because the editorial fields sit outside the key. A failed fetch, a failed parse or a mismatch is absence: the agreement, and the assembly holding it, is not offered — never a fallback to a bundled or inline copy. A withdrawn stake leaves the binding readable, so assemblies already composed from it keep hydrating; a reader offers only live registrations for a new composition.

## How an assembly composes from registered agreements

An assembly is a merkle tree of agreements, one leaf per agreement, each a registered agreement, plus the clauses composed once for the whole assembly. It registers once, so anyone who fits the shape trades through it without drawing it again. The assembly is `{ name?, summary?, description?, faq?, assemblyClauses?, agreements: ProcessDesignAgreement[] }`, each `ProcessDesignAgreement` `{ id: "agreement-<i>", agreementHash, clauses, follows }`, where `clauses` holds the fills that belong to the position (`{}` when none) and `follows` the labels `["agreement-<j>", …]` of the agreements it follows (`[]` or absent on the root). The topology is never a clause: at design time it is the entry's `follows`, at runtime the signed agreement's topology leaf.

**The root.** `processDesignHash = processDesignHashOf(assembly)` is a merkle root with the assembly tree's own leaf convention, `keccak256(keccak256(processLeafDomain ‖ key ‖ keccak256(bytes)))` with `processLeafDomain = keccak256("figaro-assembly-leaf")`, sorted-pair hashing:

- one leaf per agreement `i` (0-based, assembly order): key the agreement's `agreementHash`; bytes the canonical JSON `{"agreement":i,"clauses":{…},"follows":[…]}` (`agreementLeafBytes(slot, i)`; object keys sorted, arrays in assembly order, `follows` `[]` when absent);
- one **assembly terms leaf**, present only when `assemblyClauses` is non-empty: key `PROCESS_TERMS_LEAF_KEY` = `keccak256("figaro-assembly-terms")`; bytes the canonical JSON of `assemblyClauses`.

A one-leaf tree's root is its leaf. Agreements are ordered, so one registered agreement may hold two. **Membership is proved, never looked up:** `buildAgreementInclusionProof(assembly, i)` returns the sorted-pair proof of agreement `i`'s leaf under `processDesignHash`, and `agreementContentHash = keccak256(agreementLeafBytes(slot, i))`. `ProcessRegistry` stores the root and a URI and checks nothing about the agreements inside it; `AgreementRegistry` knows no assembly.

**An agreement carries the clauses its designer composed.** Nothing is written in: `buildProcessDesign` and `composeOrderAgreement` keep exactly the selection, value-free but for design fills, and refuse only an agreement composing no clause. No clause is required: the commitment carries the payment and the token, so an agreement that composes no clause declaring `lineItems` still carries its payment, and only the list of what the payment buys goes uncommitted. In the protocol's clause set `figaro-commerce` holds the line items, agreement-scoped; compose it where the parties commit that list. It earns for its designer of record like any other clause, wherever a designer composed it.

**The seeding order.** Clauses, then agreements, then the assembly: register each clause the agreements name, then each distinct agreement once (one stake each; skip a key already registered), then the assembly whose agreements name them.

The link from an order to the registered agreement and the assembly it instantiated is a leaf of the agreement format, not a clause: the **provenance leaf**. Its key is `PROVENANCE_LEAF_KEY`, `keccak256("figaro-agreement-provenance")` = `0x26dc18a2251a8f4629ada6df88b7c98553e011c08682d28ce5bb51a441227dc6` — the hash of a plain label, not of any spec's bytes; under keccak256's second-preimage resistance no spec has this key. `ClauseRegistry` and `ProcessRegistry` take any bytes32, so a wallet can still register it there, and accrual refuses it — and the assembly terms key — whatever a registry holds: the direct path reverts (`ReservedKeyIsNotARegistration`, `src/rewards/UsageCounter.sol`), the guest refuses a batch usage claim keyed on either (`prover/lib/src/kernel.rs`), the counter's batch path skips both, and `AgreementRegistry` refuses both as registrations. Its committed bytes are the canonical JSON `{"agreementHash":"0x<64 lowercase hex>","processDesignHash":"0x<64 lowercase hex>"}` (`provenanceLeafBytes(agreementHash, processDesignHash)`; `decodeProvenanceContent(bytes)` reads them back, or returns `null`), and it enters the merkle tree as any clause leaf does, `keccak256(keccak256(key ‖ keccak256(bytes)))` (`computeProvenanceLeaf(agreementHash, processDesignHash)`). Checkout writes both keys from the agreement the order instantiates; an agreement with no `provenance` names no assembly and has no such leaf. `UsageCounter.recordAgreementUsage` reproduces those bytes from the two keys it is given and proves the leaf against `checkoutHash`, which is how a resolved process credits the registered agreement's designer; `recordProcessDesignUsage` proves the same leaf and then the agreement's membership proof under `processDesignHash`, which is how it credits the assembly's designer ([UsageCounter](/protocol/contracts/)). While the process is open, the buyer can attest the leaf with `attestAsBuyer` (`@figaro-protocol/sdk/agent`); `provenanceLeafAttestation(agreement)` returns its inputs — the reserved key in the clause-key position, stage `0`, the inclusion proof, and the hash of the bytes as both `clauseDataHash` and `contentRef` — and the coordinator refuses any attestation once the order is resolved (`OrderResolved`, `src/core/attestation/AttestationCoordinator.sol:187`). That attestation is the buyer's declaration that the process runs a registered agreement and its assembly. On the direct path the coordinator proves the leaf from `clauseDataHash` and never ties `contentRef` to it; `provenanceLeafAttestation` is what sets the two equal. A reader checks the declaration by computing `provenanceContentRef` for registered pairs of agreement hash and assembly hash and comparing it to the attestation's `contentRef`, with no spec and no access to the agreement. The batch path accepts the same attestation on the same check, the leaf's inclusion in `checkoutHash`, as it accepts any attestation; the bytes behind the leaf's hash are checked where they are used, at the usage claim (`validate_attestation_witness`, `prover/lib/src/kernel.rs:384-405`).

The `processDesignHash` covers the composition and nothing else: a different registered agreement in the list, a re-wired topology, a different order of agreements, or different assembly-scoped terms all produce a different assembly — and a different clause set or one different design-filled value inside an agreement is a different `agreementHash`, so a different leaf; editorial prose (`name`, `summary`, `description`) is excluded, so renaming never forks it. The flip side of excluding prose: prose is not identity, so it does not protect a composition from being anchored by someone else first.

```ts
import { processDesignHashOf, deriveProcessDesignSlug } from "@figaro-protocol/sdk";

const h = processDesignHashOf(assembly);            // the registry key: the merkle root over the agreements
buildAgreementInclusionProof(assembly, 0);                   // the first agreement's membership proof under h
deriveProcessDesignSlug(h);                                  // "asm-<first 8 bytes>" — off-chain, never stored
processDesignHashOf({ ...assembly, name: "Anything" }) === h;  // true: prose is excluded
```

Compute the root from the *raw* assembly, before any buyer, catalog, or pricing fill touches it; compute it after merging those fills and you get a hash the registry never anchored.

## Document anchoring — the public/withheld seam

The chain holds fingerprints, never preimages, so each clause is anchored by its `hashClauseData` while its content lives off-chain on IPFS. A clause takes one of two forms, and the merkle leaf is identical either way:

- **Public** — the clause carries plaintext `data`, pinned as plaintext, and `hashClauseData` is computed from it. A reader fetches the bytes, hashes them back, and decodes against the spec.
- **Withheld** — the clause carries a `dataHash` fingerprint in place of `data` (paid-edge or private content), pinned encrypted. It contributes the exact same leaf, so the agreement root is unchanged — a party can publish or verify the agreement's structure while keeping the plaintext off every public surface.

**A clause carries `data` XOR `dataHash`, never both.** The hashing function refuses a clause with both, at the hashing locus, so no consumer — leaf, root, or the sign gate — can pass a clause that signs one thing and shows another (`sdk/src/agreement.ts:221-236`). Per-field disposition (`"public"` default, or `"private"`) is declared in the spec and governs publication and grain policy; the chain carries only the clause data hash either way. Withholding is fail-closed: an unknown spec, or any private field in the encoded set, publishes nothing, and a lookup that resolves empty reads as absence.

**A private set carries one blinding field.** A withheld clause still publishes its fingerprint, and the spec is public, so a private value with few possibilities could be confirmed by hashing each guess. Every set of fields that declares a private field (the top-level `fields`, or one `stages[N]`) therefore declares exactly one blinding field, at its top level:

```json
{ "name": "blinding", "type": "string", "format": "bytes32-hex",
  "required": true, "disposition": "private", "blinding": true }
```

What you declare, and what the tooling does:

1. One blinding field per private set, of exactly that shape, with no `default`; any name, since tooling reads `"blinding": true`. A set with no other private field declares none, and no set mixes public and private fields. `parseClauseSpec` refuses a spec that breaks a rule (`sdk/src/clauses/spec.ts`), and the published definition states the same (`sdk/src/clauses/clause-spec.schema.json`).
2. Name it in no fills list. The party that fills the set draws the value: the buyer's tooling at checkout, the attesting party's for a witness stage. `withClauseBlinding` and `withFreshBlinding` draw 32 random bytes through `generateSalt` where the value is absent and never overwrite one; `buildBuyerOffer`, `buildQuoteRequest`, `buildChainOffers` and `prepareAttestationContent` call them for you.
3. The sign gate (`validateCommitmentAgreement`) refuses a spec that names the blinding field in `block.design.fills`, `block.checkout.catalogueFills`, `profileFills` or `catalogueMeasures`, a zero value, and one value two clauses of the agreement share.

The value is a field like any other: it enters the canonical JSON of stage 0 and the ABI bytes of a stage, so the leaf, the `checkoutHash`, `contentRef` and its CID are computed as before, and whoever holds the content reproduces the fingerprint from the content alone. It is not a term: a form offers no input for it, and a comparison of two parties' filings reads past it. A public set carries none, so public content stays reproducible by anyone. The commitment's own `salt` is no substitute: it is the order's identity, emitted in `OrderCommitted`. No contract and no proof reads the value, on either path: the signer's tool checks it before signing (`validateCommitmentAgreement`, `prepareAttestationContent`), and a reader to whom the content is disclosed checks it against the spec its clause key names.

## Registration — permissionless, first-write-wins, ETH-staked

A new clause is a spec plus a registration, nothing else — no validator contract, no interface step. Neither path reads a spec: `AttestationCoordinator` and the proof program check a clause's leaf against the signed `checkoutHash`, whatever its key.

```solidity
function registerClause(bytes32 clauseKey, string calldata contentURI)
    external payable;   // ClauseRegistry — first-write-wins on the key, immutable, under a stake
```

The key is `computeClauseKey(spec)`, `keccak256` of the canonical bytes of the spec without its top-level `block` (`src/registries/ClauseRegistry.sol:138-142`). The registry stores no name, no version and no separate content hash: the key is the content hash. It takes the key as given and never sees the document, so a key whose bytes nobody can fetch is a registration no reader can verify (`:49-51`). Registration anchors identity and integrity only — no group field (grouping is `block.design.article`, off-chain), no reward tag (designer rewards are uniform on real use), no validator. A clause is attestable on both paths once an order commits its leaf, registered or not; registration gives discovery, and a use counts for designer rewards when the registration stake and the seller's member stake are both live, on either path (`src/rewards/UsageCounter.sol:100-118`). The stake is a deploy-time parameter: read `registrationDeposit()` live and send exactly it. `clauseId` and `version` are the spec's own labels: two specs that carry the same name are two clauses with two keys, a revision of a clause is a new spec with a new key registered beside the old one, and compatibility between two revisions, if it ever matters, is derived by diffing two immutable specs.

```ts
import { canonicalize, computeClauseKey, anchorClauseSpec } from "@figaro-protocol/sdk";

const bytes = canonicalize(spec);          // the whole raw document, block included: the bytes to pin
const clauseKey = computeClauseKey(spec);  // keccak256 of the canonical spec without its block
// read registered(clauseKey) first (same spec, same clause), pin `bytes`,
// then registerClause(clauseKey, contentURI) with value = registrationDeposit()

// A reader verifies a fetched spec by recomputing its key:
anchorClauseSpec(fetchedBytes, clauseKey); // the parsed spec, or null when computeClauseKey(parsed) != clauseKey
```

`anchorClauseSpec` parses what it fetched, drops the top-level `block`, canonicalizes and hashes (`sdk/src/anchored.ts:65`): the byte form a spec is pinned in and its `block` do not change its key. It returns the spec with the `block` it was served, which the key does not cover ([Sharp edges](/protocol/sharp-edges/)).

Withdrawing the stake de-surfaces the clause for new compositions but never deletes the binding: orders already committed against it still resolve. Agreements register the same way on `AgreementRegistry` (keyed by `agreementHash`) and assemblies on `ProcessRegistry` (keyed by `processDesignHash`), with the same permanence.

**One spec, checked by the tools that sign and read content.** No contract and no proof validates content, on either path. `AttestationCoordinator` checks who attests, that the order is open and that the clause's leaf is in the signed `checkoutHash` (`src/core/attestation/AttestationCoordinator.sol:106-187`); the proof program runs the same checks on a batched attestation, which carries exactly the coordinator's `clauseDataHash`, inclusion proof and `contentRef` (`prover/lib/src/kernel.rs:384-476`). Neither reads a spec, a content or a registry. A signer's tool validates content against the spec before signing: in this project's SDK, one such tool, `parseClauseSpec` and `validateContent` gate every signature it makes, and a builder's own tool, in any language, applies the limits the published format states (`sdk/src/clauses/clause-spec.schema.json`). A reader validates a disclosed content against the spec its clause key names. A clause nobody registered is attested alike on both paths, and a never-seen clause resolves on either with no code change. There are no per-clause validator contracts, by design — a clause is data, not code.

The contract surfaces these calls belong to — `ClauseRegistry`, `AgreementRegistry`, `ProcessRegistry`, `AttestationCoordinator`, `UsageCounter`, `FigaroBatchVerifier` — are on [The contracts](/protocol/contracts/); the reward that follows real use is on [Designer rewards](/token/designer-rewards/).
