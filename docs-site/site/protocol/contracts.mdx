Everything on this page is a permissionless primitive. No contract belongs to an app, and none has an admin, an owner, a pause, or an upgrade key. You reach them with a wallet and `cast` or `viem` over a public RPC — nothing is gated on who you are.

Read the [whole model](/) first; this page assumes it. In those terms: **`FigaroCore`** holds the two mechanisms — asymmetric bonding at commit, buyer dominance with atomic resolution — and the six nouns (buyer, seller, clause, agreement, assembly, composition) live in the data those calls carry and in the registries that anchor them. An order has exactly two operations, **commit** and **resolve**, and they happen one of two ways that share no state: the **direct path** calls `FigaroCore`; the **batch path** proves many operations at once against `FigaroBatchVerifier`. Both paths carry commit *and* resolve.

Solidity 0.8.26, MIT, at [figaro-protocol/Figaro](https://github.com/figaro-protocol/Figaro). Every fact below is cited to the source line a builder would read; nothing here asks you to edit a repository file — the path is the chain, the SDK, and IPFS.

## Install the client

`@figaro-protocol/sdk` builds the EIP-712 commitments, reconstructs process state from events, and computes every hash on this page, over `viem` as a peer dependency:

```bash
npm install @figaro-protocol/sdk viem
```

You do not need it — every call below is reachable with raw `cast` — but it is the difference between signing a struct by hand and calling `buildCommitment`. Its manual is the [SDK page](/building/sdk/); its generated API reference is at [`/sdk-api/`](/sdk-api/index.html).

## FigaroCore

`FigaroCore` holds every deposit and resolves a process on its buyer's signature. It reads no contract above it and has no third entry point (`src/core/kernel/FigaroCore.sol:26`).

**Two state-changing functions:**

```solidity
function commit(CommitmentTypes.Commitment calldata c, bytes calldata buyerSig, bytes calldata sellerSig)
    external returns (bytes32 processId, bytes32 orderHash);          // src/core/kernel/FigaroCore.sol:148

function resolveProcess(bytes32 processId, CommitmentTypes.Commitment[] calldata commitments)
    external;                                                          // src/core/kernel/FigaroCore.sol:262
```

Both are `nonReentrant`. `commit` verifies both EIP-712 signatures over `c`, then pulls `2 × payment` from the buyer and `2 × expectedCumulativeValue` from the seller. A root order (`c.processId == 0`) opens a process; any other order extends one and must carry the same `c.buyer` as the process's root buyer and an `expectedCumulativeValue` equal to the live accumulator plus this order's `payment`. `resolveProcess` requires `msg.sender` to be the root buyer and the complete active-order list, then pays every seller `2 × expectedCumulativeValue + payment` and refunds the buyer `payment` — every deposited token leaves in one call; `FigaroCore` never holds a withdrawable balance.

**Public reads:** `orderStatus(bytes32 orderHash) → uint8` (0 unknown, 1 committed, 2 resolved), `orderProcessId(bytes32) → bytes32`, the `processes` mapping (`ProcessState{rootBuyer, currency, cumulativeValue, activeOrderCount}`), and `DOMAIN_SEPARATOR() → bytes32` (`src/core/kernel/FigaroCore.sol:52-115`). `orderStatus` answers for the **direct path only** — a batch-resolved order reads `0` here forever, so `0` means "not on this path," never "not resolved."

**The EIP-712 domain is `{ name: "FigaroCore", version: "3", chainId, verifyingContract }`** (`src/core/kernel/FigaroCore.sol:107`). The version counts changes to the commitment struct's layout, not deploys.

**Custom errors** (`src/core/kernel/FigaroCore.sol:64-79`): `DeadlineExpired`, `InvalidBuyerSignature`, `InvalidSellerSignature`, `ZeroPayment`, `ProcessAlreadyExists`, `UnknownProcess`, `CumulativeValueMismatch(expected, actual)`, `NotProcessBuyer`, `CurrencyMismatch`, `OrderNotCommitted(orderHash)`, `NoActiveOrders`, `IncompleteOrderList(required, provided)`, `DuplicateCommitment`, `FeeOnTransferDetected`, `InvalidRootCumulativeValue`, `ProcessAlreadyResolved`. Decode them by name with `CORE_ABI` from `@figaro-protocol/sdk`, which also carries the standard ERC-20 error fragments (`ERC20InsufficientAllowance` shows up when a sub-order approval falls short — `FigaroCore` pulls the full per-order bond every time and nets nothing against bonds it already holds).

**Events:** `OrderCommitted` (carries every struct field but no signatures — the signature bytes live in the commit transaction's calldata), `OrderSeller`, `OrderCurrency`, `OrderResolved`, `ProcessResolved` (`src/core/kernel/FigaroCore.sol:35-60`).

### Calling it from the chain

The denomination is an ordinary ERC-20 named in `c.currency`; approve `FigaroCore` for the full bond before you commit. With the SDK doing the EIP-712 signing:

```ts
import { createWalletClient, http } from "viem";
import { buildCommitment, CORE_ABI } from "@figaro-protocol/sdk";

// both parties sign the same struct as EIP-712 typed data over the
// { name: "FigaroCore", version: "3", chainId, verifyingContract: core } domain
const { commitment, buyerSig, sellerSig } = /* buildCommitment + two signTypedData calls */;

await wallet.writeContract({
  address: core, abi: CORE_ABI, functionName: "commit",
  args: [commitment, buyerSig, sellerSig],
});
```

To resolve, rebuild the full active-order set from `OrderCommitted` events (nothing has to be kept client-side) and call `resolveProcess(processId, commitments)` from the buyer wallet. Build every `deadline` from chain time, not host time, or you race `DeadlineExpired`.

## CommitmentTypes — the signed struct

`CommitmentTypes` is the shared struct-and-hashing library both `FigaroCore` and its coordinators import (`src/core/kernel/CommitmentTypes.sol:19`). One `Commitment` covers root and sub-orders:

```solidity
struct Commitment {
    bytes32 processId;   // 0 for a root order
    address buyer;
    address seller;
    address currency;    // the ERC-20 denomination
    uint256 payment;
    uint256 expectedCumulativeValue;
    bytes32 checkoutHash;  // merkle root of the order's composed clauses
    uint256 salt;        // makes a repeat order hash distinctly
    uint256 deadline;    // commit window; a signature ages out, it never expires post-commit
}
```

`checkoutHash` is the seam to the [clause and agreement model](/protocol/clauses/): it is the merkle root over the order's composed clauses, and it is what offer and acceptance — the two signatures — are taken over. The `COMMITMENT_TYPEHASH` string is exported as `COMMITMENT_TYPES` from the SDK; never retype it.

## ClauseRegistry — anchoring a clause

Permissionless, first-write-wins clause anchoring under a stake (`src/build/registries/ClauseRegistry.sol`). It anchors a clause key and a locator only; it validates no content shape — a registered clause is immediately attestable and batch-resolvable.

```solidity
function registerClause(bytes32 clauseKey, string calldata contentURI)
    external payable;                          // src/build/registries/ClauseRegistry.sol:150
function withdrawDeposit(bytes32 clauseKey) external;     // :173
function setMechanismClause(bytes32 clauseKey) external;  // :192
function registered(bytes32 clauseKey) external view returns (bool);                        // :81
function depositOf(bytes32 clauseKey) external view returns (address registeredBy, bool withdrawn);  // :92
```

The key is `clauseKey = keccak256` of the spec's pinned bytes — the SDK's `computeClauseKey(spec)`, over the canonical JSON `canonicalize(spec)` you pin at `contentURI` (`:146-149`). The key is the clause's identity and its content hash at once; the registry stores no name, no version and no separate hash, and a reader verifies a fetched spec by checking `keccak256(bytes) == clauseKey` on the bytes it fetched (`:11-20`). `registered(clauseKey)` is never cleared, because it is what `FigaroBatchVerifier` checks every witness spec's key against. `withdrawDeposit` is caller-only, once, no time lock: it refunds the stake and de-surfaces the clause for new compositions, but the binding is permanent and orders already committed against it still resolve. `setMechanismClause` is permissionless self-declaration that writes no storage and confers nothing — it emits `MechanismClauseSet(msg.sender, clauseKey)` so indexers can see which clause a composed mechanism speaks.

`registrationDeposit()` is a deploy-time immutable — **read it live and send exactly it**; over-payment reverts too, because there is no sweep (`src/build/registries/ClauseRegistry.sol:74`).

**Errors** (`:125-132`): `AlreadyRegistered(clauseKey)`, `NotRegistered(clauseKey)`, `ZeroClauseKey`, `EmptyContentURI`, `WrongDeposit(provided, required)`, `NotRegisteredBy(caller, registeredBy)`, `AlreadyWithdrawn`, `TransferFailed`. **Events:** `ClauseRegistered(bytes32 indexed clauseKey, string contentURI, address indexed registeredBy)`, `DepositWithdrawn(clauseKey, registeredBy, amount)`, `MechanismClauseSet(mechanism, clauseKey)` (`:107-121`).

```bash
# CLAUSE_KEY = computeClauseKey(spec); CID = the pin of canonicalize(spec), exactly those bytes
cast call $CLAUSE_REGISTRY "registered(bytes32)(bool)" $CLAUSE_KEY --rpc-url $RPC
# read the required stake, then register (deposit is deploy-time; never assume a number)
cast call $CLAUSE_REGISTRY "registrationDeposit()(uint256)" --rpc-url $RPC
cast send $CLAUSE_REGISTRY \
  "registerClause(bytes32,string)" \
  $CLAUSE_KEY "ipfs://$CID" \
  --value $DEPOSIT --rpc-url $RPC --private-key $PK
```

## AgreementRegistry — anchoring a agreement

Permissionless, first-write-wins anchoring of a agreement — the clauses composed for one agreement with the designer's fills, value-free — under a stake (`src/build/registries/AgreementRegistry.sol`). A registered agreement is the reusable unit an assembly is composed from; identity *is* the composition.

```solidity
function registerAgreement(bytes32 agreementHash, string calldata contentURI) external payable;  // :159
function withdrawDeposit(bytes32 agreementHash) external;                                         // :188
function bindings(bytes32 agreementHash) external view
    returns (address registeredBy, uint64 registeredAt, bool depositWithdrawn, string memory contentURI);
function registrationDeposit() external view returns (uint256);
function PROVENANCE_LEAF_KEY() external view returns (bytes32);      // :78  (refused as a key)
function ASSEMBLY_TERMS_LEAF_KEY() external view returns (bytes32);  // :83  (refused as a key)
```

`agreementHash` is the merkle root over one leaf per composed clause, `keccak256(keccak256(clauseKey ‖ keccak256(fills)))` under the agreement format's leaf convention — `agreementHashOf(doc)` in the SDK, with `buildRegisteredClauseInclusionProof` for a clause's membership — over the agreement's `clauses` (clause key → the designer's fills, the topology clause composed with `{}`); the document's `name`, `summary` and `description` are excluded, so identical compositions collapse to one binding. The key is design-time: it is never the `checkoutHash` a commitment carries. Pin the agreement, then register its key; a reader fetches the document from `contentURI`, parses it, and accepts it only if `agreementHashOf(doc)` equals the registered key — a failed fetch, parse or match is absence, never a fallback. Withdrawal refunds the stake and de-surfaces the agreement for new compositions; the binding stays, so every assembly already composed from it keeps hydrating. The registry references no other contract.

**Errors**: `EmptyContentURI`, `ZeroAgreementHash`, `ReservedKeyIsNotARegistration(key)` (the two reserved keys of the agreement format, `keccak256("figaro-agreement-provenance")` and `keccak256("figaro-assembly-terms")`), `AgreementAlreadyRegistered(agreementHash)`, `WrongDeposit(provided, required)`, `NotRegistered`, `NotRegisteredBy(caller, registeredBy)`, `AlreadyWithdrawn`, `TransferFailed`. **Events:** `AgreementRegistered(bytes32 indexed agreementHash, address indexed registeredBy, string contentURI)`, `DepositWithdrawn(bytes32 indexed agreementHash, address indexed registeredBy, uint256 amount)`.

```bash
# AGREEMENT_HASH = agreementHashOf(doc); CID = the pin of the agreement document
cast call $AGREEMENT_REGISTRY "bindings(bytes32)(address,uint64,bool,string)" $AGREEMENT_HASH --rpc-url $RPC
cast call $AGREEMENT_REGISTRY "registrationDeposit()(uint256)" --rpc-url $RPC
cast send $AGREEMENT_REGISTRY \
  "registerAgreement(bytes32,string)" \
  $AGREEMENT_HASH "ipfs://$CID" \
  --value $DEPOSIT --rpc-url $RPC --private-key $PK
```

## AssemblyRegistry — anchoring an assembly

Permissionless, first-write-wins assembly anchoring under a stake (`src/build/registries/AssemblyRegistry.sol`). Identity *is* the composition.

```solidity
function registerAssembly(bytes32 assemblyHash, string calldata contentURI) external payable;  // :148
function withdrawDeposit(bytes32 assemblyHash) external;                                        // :175
```

`assemblyHash` is a merkle root over the assembly's agreements, built with the assembly tree's own leaf convention (`keccak256(keccak256(assemblyLeafDomain ‖ key ‖ keccak256(bytes)))`, `assemblyLeafDomain = keccak256("figaro-assembly-leaf")`, sorted-pair hashing; the agreement format's leaf carries no domain, so the two trees never share a shape): one leaf per agreement `i`, key the agreement's `agreementHash`, bytes the canonical JSON `{"clauses":{…},"slot":i}` (the agreement's own fills — the topology clause's `follows`); and, when any assembly-scoped clauses are composed, one leaf keyed `keccak256("figaro-assembly-terms")` over the canonical JSON of `assemblyClauses`. Editorial prose is excluded, so identical compositions collapse to one binding and no caller-chosen name exists on chain; the human slug is derived off-chain. Membership of an agreement in an assembly is a merkle proof of its agreement leaf under the root — the registry stores no list and checks nothing about the agreements a root names. `bindings(assemblyHash)` returns `(address registeredBy, uint64 registeredAt, bool depositWithdrawn, string contentURI)` — everything the chain stores for the binding. Withdrawal refunds the stake and de-surfaces the assembly; the binding stays, because buyers and sellers referencing it rely on stable content.

**Errors** (`:120-127`): `EmptyContentURI`, `ZeroAssemblyHash`, `AssemblyAlreadyRegistered(assemblyHash)`, `WrongDeposit(provided, required)`, `NotRegistered`, `NotRegisteredBy(caller, registeredBy)`, `AlreadyWithdrawn`, `TransferFailed`. **Events:** `AssemblyRegistered`, `DepositWithdrawn`. Compute the root off-chain with `assemblyHashOf(assembly)` from the SDK, and a agreement's membership proof with `buildAgreementInclusionProof(assembly, i)` — see [Clauses and agreements](/protocol/clauses/).

## MembersRegistry — a participant declaration

Permissionless self-registration under a reclaimable stake — one declaration document per wallet, whichever side of a trade it takes (`src/app/MembersRegistry.sol`).

```solidity
function register(string calldata metadataURI) external payable;   // :142
function updateProfile(string calldata metadataURI) external;      // :162
function requestWithdrawal() external;                             // :179
function withdraw() external;                                      // :194
function registered(address member) external view returns (bool);  // :120
function withdrawable(address member) external view returns (bool);// :131
```

Withdrawal is two steps: `requestWithdrawal()` de-lists you at once and schedules the stake, `withdraw()` releases it after `withdrawalCooldown` elapses — so one stake cannot serve identity after identity. `registered(address)` is the seller-side gate `UsageCounter` reads for designer rewards. Availability is signaled off-chain, never as registry state — there is no active flag, no role field.

**Errors** (`:92-97`): `AlreadyRegistered`, `NotRegistered`, `InsufficientDeposit` (the exact-match deposit check, despite the name), `NothingPending`, `CooldownActive(releaseAt)`, `TransferFailed`. **Events:** `MemberRegistered`, `MemberProfileUpdated`, `MemberWithdrawalRequested`, `MemberWithdrawn`.

The four registries carry no edges among themselves — parallel anchors, never nested. Assembly→agreement, agreement→clause and seller→assembly relationships are off-chain: assemblies use agreements, agreements use clauses, and neither knows what uses it.

## AttestationCoordinator — evidence while an order is live

Zero-storage, merkle-only attestation bound to the signed `checkoutHash` (`src/core/attestation/AttestationCoordinator.sol`). It composes `FigaroCore` without becoming a party: it reads `orderStatus` and `DOMAIN_SEPARATOR`, and enforces nothing about resolution.

```solidity
function attestAsSeller(
    CommitmentTypes.Commitment calldata target,
    bytes32 clauseId, uint8 stage, bytes32 clauseDataHash, bytes32[] calldata proof, bytes32 contentRef
) external;                                    // :105
function attestAsBuyer(
    CommitmentTypes.Commitment calldata target,
    bytes32 clauseId, uint8 stage, bytes32 clauseDataHash, bytes32[] calldata proof, bytes32 contentRef
) external;                                    // :127
```

`attestAsSeller`'s caller must equal `target.seller`: a seller attests about a clause of its own order. `attestAsBuyer`'s caller must equal `target.buyer`. A party attests for itself. Every call carries fingerprints, never preimages: `clauseDataHash = keccak256(clauseData)`, `contentRef = keccak256(content)`. The coordinator verifies a merkle inclusion proof of `leaf = keccak256(keccak256(clauseId || clauseDataHash))` against `target.checkoutHash`, then emits `Attestation(orderHash, processId, attester, clauseId, stage, contentRef)`. A clause not committed at signing cannot be attested; a never-seen clause is attestable with zero per-clause code.

The coordinator checks that the caller is the named order's seller or buyer, that the clause sits under the agreement both parties signed, and that the order is committed and not yet resolved. It emits `contentRef` as given and never reads the content behind it. An attestation is the attester's representation: the chain proves who made it, against which order, and when, never that it is true. What stands behind a seller's attestation is the buyer's decision: a buyer who finds it false before resolving can withhold resolution, which keeps the seller's bond locked, and its own, and pays nobody, until it is put right; co-sellers whose own payment waits on the same resolution have their own reason to press. A buyer's own attestation meets no such pressure. After resolution, which no one can reverse, the attestation stays in the public data and in its signer's resolution history. Parties acting together are outside that reach.

**Errors** (`:87-90`): `NotAuthorized`, `UnknownOrder`, `OrderResolved`, `InvalidInclusionProof(checkoutHash, clauseId)`. Build the proof with `buildSignedClauseInclusionProof` from the SDK, over the agreement that was actually signed.

## WitnessSwapAndCommitCoordinator — bond in a token you do not hold

Direct-path only. Lets a buyer and/or seller fund a bond from a token other than the process's denomination, in the same transaction as `commit` (`src/app/WitnessSwapAndCommitCoordinator.sol`).

```solidity
function swapAndCommit(
    CommitmentTypes.Commitment calldata c, bytes calldata buyerSig, bytes calldata sellerSig,
    SwapFunding calldata buyerFunding, SwapFunding calldata sellerFunding
) external returns (bytes32 processId, bytes32 orderHash);   // :180
function swapWitness(address inputToken, uint256 maxInput, bytes calldata swapData)
    external view returns (bytes32);                          // :170
```

For each enabled leg it pulls the input token through a Permit2 witness signature, forwards the swap calldata to an immutable Uniswap `SwapRouter02`, sends the swapped denomination to the party's own address, then calls `FigaroCore.commit`. Bond amounts derive from `c` (`2·payment`, `2·expectedCumulativeValue`), never from calldata; the witness binds `{router, inputToken, maxInput, keccak256(swapData)}` so no relayer can reroute the swap. `FigaroCore` still sees a single-currency, bilaterally-signed commitment. On the batch path there is no funding leg — swap in your own wallet before submitting.

**The venue is SwapRouter02, and the distinction is load-bearing for the calldata you sign.** The coordinator approves the router for your input token and forwards your `swapData` verbatim (`src/app/WitnessSwapAndCommitCoordinator.sol:221-224`), so the venue must pull by ERC-20 allowance: the calldata is SwapRouter02's `exactOutputSingle` — an exact output, the bond, for at most `maxInput` of input (`:135`) — not the Universal Router, which pulls through Permit2 or spends pre-sent balances and would leave the swap unfunded. Build it with the SDK's `SWAP_ROUTER_02_ABI`, which carries exactly the venue shapes the protocol composes.

**Errors** (`:153-155`): `NothingToFund`, `SwapCallFailed`, `OutputBelowBond(received, required)`. Per-party prerequisites: a one-time `approve(FigaroCore, …)` for the denomination, a one-time `approve(Permit2, …)` for the input token, and a per-commit Permit2 witness signature.

## FigaroBatchVerifier — the batch path

Resolves batches of `FigaroCore` operations beside the direct path, under one SP1 validity proof (`src/core/verifier/FigaroBatchVerifier.sol`). It applies commit *and* resolve — the whole lifecycle executes inside the proof.

```solidity
function settleBatch(
    bytes calldata proof, bytes calldata publicValues,
    NetPosition[] calldata positions, BatchEventData calldata events, BatchUsageData calldata usage,
    bytes calldata operations
) external;                                    // :292  (nonReentrant, external, no caller gate)
```

`settleBatch` verifies the proof against the immutable `programVKey`, checks state-root continuity and chain binding, hash-verifies the calldata byte-for-byte, checks every spec binding — the guest commits `(clause key, keccak256(witness-spec bytes))` for each spec it validated content against, one per clause a plaintext attestation names (a hash-only attestation, the default, commits none, as the coordinator consults no registry), and the verifier requires the two words equal and `ClauseRegistry.registered(clauseKey)` (`:634-642`); the vkey covers the generic clause engine, the registry anchors the constraint set, so a new clause never touches the prover — then moves each net token position with at most one transfer (pulls `deposit − payout` from a position that owes, pushes `payout − deposit` to one that is owed, nothing when the two are equal), re-emits proven `Attestation` events, and forwards usage accrual to `UsageCounter.applyBatchAccrual`. Public state is `stateRoot() → bytes32` and `batchCount() → uint64`, advanced per `BatchSettled`.

**The public values are ten 32-byte words** (`src/core/verifier/FigaroBatchVerifier.sol:73-90`): `prevStateRoot`, `newStateRoot`, `chainId`, `verifyingContract`, `tokenOpsHash`, `attestationEventsHash`, `specBindingsHash`, `usageAccrualHash`, word 8 **`blockTimestamp`** (uint64), and word 9 **`operationsHash`**, the keccak of the batch's operation stream — every commit and resolve the batch applied, whole, and every usage claim — which `settleBatch` takes as its last calldata argument and refuses to land without (`OperationsHashMismatch`), so the state behind any root can be rebuilt from the chain alone. Word 8 is bounded: `settleBatch` reverts unless `blockTimestamp <= block.timestamp` and `block.timestamp - blockTimestamp <= MAX_BATCH_STALENESS`, where `MAX_BATCH_STALENESS = 1 hours` (`:109`, `:325`). It pins the clock the guest checked deadlines against to reality — a batch is proven then submitted, so a few minutes of lag is normal — while stopping a caller from picking an arbitrary past time to bond an already-expired commitment.

**What a batch publishes beside its proof.** The operation stream (every commit and resolve the batch applied, whole, and every usage claim) is the last calldata argument, hash-bound to word 9; the verifier reads it and emits, for every commit, `OrderSeller`, `OrderCurrency` and `OrderCommitted`, and for every resolution `OrderResolved` per order and `ProcessResolved` — the Core's own events, with the order and process ids derived under the verifier's EIP-712 domain (`FigaroCore` version 3 at the verifier's address, the domain the batch's signatures were made under). It also logs the stream itself with the clock, usage period and provenance leaf its replay needs (`BatchOperations`), so the state behind any root is rebuilt from the verifier's own logs, however the call reached it; a relay started with `REBUILD_FROM_CHAIN=1` does it. The state root starts at `genesisRoot()`, the empty state's, computed by the contract and never supplied.

**Errors** (`:212-233`): `PublicValuesLengthMismatch(expected, actual)` — the public values are not the 320 bytes of ten words, refused before the proof is read; `OperationsHashMismatch` — the operation stream sent is not the one the proof committed; `StateRootMismatch(expected, actual)`, `ChainIdMismatch(expected, actual)`, `VerifyingContractMismatch(expected, actual)`, `PositionHashMismatch`, `AttestationHashMismatch`, `SpecBindingsHashMismatch`, `UsageAccrualHashMismatch`, `BatchTimestampOutOfRange(committed, current)`, `SpecBindingMismatch(clauseId, proven)` (a witness spec whose hash is not the key it names), `ClauseNotRegistered(clauseId)` (a key the registry never registered), `FeeOnTransferDetected`. **Events:** `BatchSettled(batchId, prevStateRoot, newStateRoot, positionCount)`, `BatchAccrualSkipped(batchId, reason)`, and `Attestation` — which **shares its topic hash with the coordinator's, so filter by contract address, not by topic** (`:199`).

### The two paths share no state

A batch-resolved process never acquires `FigaroCore` status: `core.orderStatus` stays `0` for it, permanently, and there is no migration between the two. The single thing that crosses is the usage accrual for designer rewards. `settleBatch` is `external` with no caller gate — anyone who can produce the proof may land it — but producing the proof is the work a **sequencer** relay does for you. The relay is transport, not an authority; its powers are to delay, to censor, and to withhold the state its batches are built on. A batch-path signature names `FigaroBatchVerifier` as its EIP-712 `verifyingContract` and does not verify on `FigaroCore`: going direct opens a new process on `FigaroCore`, signed for its domain, while a process already open on the batch path resolves only through a batch built on the state behind the verifier's root. Its wire protocol and the read endpoints (which mirror `FigaroCore` events a batch-resolved order does not emit) are on the [SDK page](/building/sdk/) and in [`docs/SCALING_STRATEGY.md`](https://github.com/figaro-protocol/Figaro/blob/main/docs/SCALING_STRATEGY.md).

Running your own relay, as opposed to using one, is the one advanced path that is not public-surface-only: the proving apparatus is the repository's `prover/` Rust workspace, and its reproducible build and run recipe are in [`prover/README.md`](https://github.com/figaro-protocol/Figaro/blob/main/prover/README.md) and [`prover/sequencer/README.md`](https://github.com/figaro-protocol/Figaro/blob/main/prover/sequencer/README.md). Because `settleBatch` is permissionless, a relay adds throughput, never trust.

| Question | Direct — `FigaroCore` | Batch — `FigaroBatchVerifier` |
|---|---|---|
| Get onto the path | broadcast `commit`, then `resolveProcess` | submit signed structs to a sequencer; it proves and calls `settleBatch` |
| Is this order resolved? | `orderStatus(bytes32) == 2` | no per-order flag; the transfers under `stateRoot()` are the proof — ask a relay for the per-order answer, verify against the chain |
| Resolution event | `OrderResolved` · `ProcessResolved` | the same `OrderResolved` · `ProcessResolved`, emitted by the verifier from the batch's operation stream (filter by address), and `BatchSettled` for the batch |
| Per-order evidence | `Attestation` from the coordinator | `Attestation` re-emitted by the verifier (same topic — filter by address); `OrderCommitted` · `OrderSeller` · `OrderCurrency` emitted by the verifier for every commit in the stream, ids derived under its own domain |
| Designer-reward credit | `UsageRecorded` / `accrualOf(kind, key, period)` | `BatchUsageRecorded` / `batchAccrualOf(kind, key, period)` |
| Total usage score | `UsageCounter.scoreOf(kind, clauseOrAssembly, period)` — sums both paths | same |

## UsageCounter — verified clause, agreement and assembly usage

Counts how much real trade a clause, a registered agreement or an assembly carried, on chain, at the moment it happens — because the Core calls no registry and contracts cannot read events, the fact is recorded when it occurs, never reconstructed afterward (`src/build/rewards/UsageCounter.sol`).

```solidity
function recordClauseUsage(CommitmentTypes.Commitment calldata order, bytes32 clauseOrAssembly,
    bytes32 clauseDataHash, bytes32[] calldata proof) external;                     // :491  (kind 0, clause)
function recordAgreementUsage(CommitmentTypes.Commitment calldata order, bytes32 agreementHash,
    bytes32 assemblyHash, bytes32[] calldata proof) external;                 // :534  (kind 2, agreement)
function recordAssemblyUsage(CommitmentTypes.Commitment calldata order, bytes32 assemblyHash,
    bytes32 agreementHash, bytes32 slotContentHash,
    bytes32[] calldata leafProof, bytes32[] calldata membershipProof) external;  // :572  (kind 1, assembly)
function applyBatchAccrual(uint8 period, bytes32 claimedProvenanceLeaf,
    BatchAccrual[] calldata accruals, address[] calldata sellers) external;      // :680  (batchVerifier only)
// struct BatchAccrual { bytes32 clauseOrAssembly; uint8 kind; uint64 c; uint64 d; }  // :642
function provenanceLeaf() external view returns (bytes32);                       // :188  (constant)
function assemblyTermsLeaf() external view returns (bytes32);                    // :198  (constant)
function assemblyLeafDomain() external view returns (bytes32);                   // :207  (constant, the assembly tree's leaf domain)
function agreements() external view returns (address);                           // :128  (the AgreementRegistry the kind-2 gate reads)
function KIND_CLAUSE() external view returns (uint8);                            // :161  (constant 0)
function KIND_ASSEMBLY() external view returns (uint8);                          // :164  (constant 1)
function KIND_AGREEMENT() external view returns (uint8);                         // :167  (constant 2)
function scoreOf(uint8 kind, bytes32 clauseOrAssembly, uint8 period) external view returns (uint256);  // :468
function accrualOf(uint8 kind, bytes32 clauseOrAssembly, uint8 period)
    external view returns (uint64 c, uint64 d, uint256 score);                   // :242  (direct path)
function currentPeriod() external view returns (uint8);                          // :449
function periodClosed(uint8 period) external view returns (bool);                // :459
function periodCount() external view returns (uint256);                          // :444
```

Every accrual, count and score is keyed by `(kind, key)`: kind `0` is a clause key, kind `1` an assembly `assemblyHash`, kind `2` a registered agreement's `agreementHash`. A registry takes any bytes32 but its reserved keys and nothing in a key's bytes names its family, so each kind's gate reads its own registry only — `recordClauseUsage` checks `ClauseRegistry`, `recordAgreementUsage` checks `AgreementRegistry`, `recordAssemblyUsage` checks `AssemblyRegistry`, and a batch accrual is gated by the registry its `kind` names. A wallet that registers an assembly's `assemblyHash` as a clause key or an agreement hash earns nothing of that assembly's accrual.

`recordClauseUsage` proves from state the chain already holds that the order is RESOLVED (`orderStatus == 2`) and that the clause was merkle-committed in the signed `checkoutHash` — the same leaf shape the coordinator checks, with the status gate inverted. `recordAgreementUsage` takes no clause data hash: it rebuilds the order's provenance leaf from the two keys it is given — key `provenanceLeaf()` = `keccak256("figaro-agreement-provenance")`, bytes `{"agreementHash":"0x<64 lowercase hex>","assemblyHash":"0x<64 lowercase hex>"}` — proves it against `checkoutHash`, and requires a live `AgreementRegistry` binding. `recordAssemblyUsage` proves the same leaf with `leafProof`, refuses an `agreementHash` equal to either reserved key, then proves the assembly tree's leaf `keccak256(keccak256(assemblyLeafDomain ‖ agreementHash ‖ slotContentHash))` under `assemblyHash` with `membershipProof`, and requires a live `AssemblyRegistry` binding (the leaf and the root are on [Clauses and agreements](/protocol/clauses/)). Every committed clause key earns, the mandatory ones included. The two reserved keys earn nothing whatever a registry holds at them: the direct path reverts (`ReservedKeyIsNotARegistration`), and the batch path skips both. Anyone may call; the proof is trusted, never the caller. Per clause, agreement or assembly per period it keeps `c` (distinct resolved processes), `d` (distinct live-staked sellers of record), and `score = icbrt(c·d²·1e18)` when `d ≥ minSellers`, else zero. Uniform — no tag, category, or weight. Usage counts only for a live-staked seller of record; a process counts once ever. Read `scoreOf`, which sums both paths' scores — `accrualOf` alone under-reports any key whose trade moved to batches.

**Runtime errors**: `ClauseAgreementOrAssemblyNotRegistered(clauseOrAssembly)` (on the batch path an un-live key is skipped, never reverted, so the batch's resolution still lands), `AccrualClosed` (`currentPeriod()` reverts once the last period ends — the revert is the answer), `UnknownOrder`, `OrderNotResolved`, `AlreadyCounted`, `InvalidInclusionProof`, `SellerNotStaked(seller)`, `NotBatchVerifier`, `PeriodMismatch(open, claimed)`, `ProvenanceLeafMismatch(expected, claimed)` (the batch's claimed provenance leaf key is not `provenanceLeaf()`), `ReservedKeyIsNotARegistration(key)` (either reserved key, on any kind), `InvalidMembershipProof` (the agreement's leaf is not under `assemblyHash`), `AccrualWentBackwards(clauseOrAssembly)`. **Events:** `UsageRecorded` (adds), `BatchUsageRecorded` (cumulative, replaces) — both carry the `kind`, and indexers fold them differently.

## FlorinToken — the unit

ERC-20 with EIP-2612 permit (`src/build/florin/FlorinToken.sol`). `MAX_SUPPLY` of one billion, enforced on every mint. It is not a call surface for a stranger: `mint` is gated to registered minters, and the minter registry is closed by `renounceDeployerMint` at genesis.

```solidity
function registerMinter(address minter, uint256 cap) external;    // :51  (deployer, pre-renounce)
function mint(address to, uint256 amount) external;               // :64  (registered minter only)
function renounceDeployerMint() external;                         // :79
```

**Errors** (`:18-24`): `NotMinter`, `DeployerMintRenounced`, `ZeroAddress`, `SupplyCapExceeded`, `MinterAlreadySet`, `MinterNotRegistered`, `MinterCapExceeded`. A florin carries no rights of any kind; nothing is minted on resolution. Allocation and the token argument are on the [florin page](/token/florin/).

## RpgfMinter — claiming designer rewards

Rewards designers of record from a 600M-florin reserve, pro rata to real recorded usage (`src/build/rewards/RpgfMinter.sol`). One state-changing entry point:

```solidity
struct ClauseOrAssemblyKey { uint8 kind; bytes32 key; }                                    // :129
function claim(uint8 periodId, ClauseOrAssemblyKey[] calldata clausesOrAssemblies) external;  // :244
function claimable(uint8 periodId, address account, ClauseOrAssemblyKey[] calldata clausesOrAssemblies)
    external view returns (uint256);                                                       // :216
```

`claim` mints `periodAmount · callerScore / totalScoreInPeriod`, once per wallet per period, and requires the period closed — so a share is score-over-total against numbers that stopped moving, no snapshot or history walk. The claimant holds a live `MembersRegistry` stake (`NotLiveMember` otherwise, read before any key; `claimable` quotes a non-member zero): a designer is rewarded only while it is a member, as a seller's usage counts only while it is one. A wallet passes every clause, agreement and assembly it designed in one call, as `(kind, key)` pairs duplicate-free in `(kind, key)`: kind `0` (`KIND_CLAUSE`) with a clause key, kind `1` (`KIND_ASSEMBLY`) with a `assemblyHash`, kind `2` (`KIND_AGREEMENT`) with an `agreementHash`. Each entry is verified against the one registry its kind names and never another (`ClauseRegistry.depositOf` for kind 0, `AssemblyRegistry.bindings` for kind 1, `AgreementRegistry.bindings` for kind 2; `registeredBy == caller` and not withdrawn; a kind above 2 reverts `UnknownKind`), and its score is read from the counter's storage slot for that kind. The SDK exports the pair as `UsageKey` and the kinds as `USAGE_KIND_CLAUSE` / `USAGE_KIND_ASSEMBLY` / `USAGE_KIND_AGREEMENT`; `computeRpgfAllocations` returns each wallet's list as `allocation.claims`. This is the designer-side half of a two-sided live-stake gate; the seller-side half is `UsageCounter`'s.

**Errors** (`:154-169`): `NotLiveMember(account)`, `UnknownPeriod(periodId)`, `PeriodStillAccruing(periodId)`, `AlreadyClaimed(periodId, account)`, `NoClausesOrAssemblies`, `DuplicateClauseOrAssembly(kind, clauseOrAssembly)`, `NotAuthorOfRecord(kind, clauseOrAssembly, caller)`, `UnknownKind(kind)`, `NothingToClaim`, `PeriodBudgetExceeded(periodId)`. The schedule and formula are on [Designer rewards](/token/designer-rewards/); this page states the surface, not the schedule.

## Composed, not owned

The deployment record also wires external canonical contracts `FigaroCore` neither knows nor depends on: Uniswap's **Permit2** and **SwapRouter02** (the swap coordinator composes these), the **SP1 verifier** Succinct's gateway routes for this release's proofs (the batch verifier binds that routed contract, never the gateway: its constructor probes `VERIFIER_HASH()` and refuses a contract without one, so no route owner can freeze a proven batch's resolution), the **DAO treasury Safe**, and the canonical **Disperse** multisender at `0xD152f549545093347A162Dce210e7293f1452150` (the same address across chains) — post-resolution batch dispersal a wallet composes to split its own receipts. Addresses are deployment configuration, never code. On a local development run these are stood in by interface-matching mocks; wherever a network names the real one, the record wires it.

## Canonical deployments

Addresses are deploy-time configuration, published in a per-chain deployment record — never hardcode them, and never quote a deposit or gas figure as mainnet-stable, since each is a deploy-time parameter.

| Network | Chain ID | Where the addresses are |
|---|---|---|
| Local Anvil | `31337` | the local run's own deployment record, handed to you by the run |
| Ethereum Sepolia | `11155111` | the committed public deployment record: [`deployments/11155111.json`](https://github.com/figaro-protocol/Figaro/blob/main/deployments/11155111.json) |

Fetch the public deployment record and hash it to confirm the site and the repository serve the same bytes:

```bash
curl -s https://raw.githubusercontent.com/figaro-protocol/Figaro/main/deployments/11155111.json | shasum -a 256
```

Before you sign a commit, the checkout shows a fingerprint of the on-chain addresses the site was built with — the `sha256:` value beneath the place-order button. It is derived, never stored, over the exact fifteen address fields below; reproduce it from the canonical deployment record and compare:

```bash
curl -s https://raw.githubusercontent.com/figaro-protocol/Figaro/main/deployments/11155111.json \
  | jq -j '{assemblyRegistry,agreementRegistry,attestationCoordinator,batchVerifier,clauseRegistry,figaroCore,florinToken,membersRegistry,multisender,permit2,rpgfMinter,swapQuoter,swapRouter,usageCounter,witnessSwapAndCommitCoordinator}
      | to_entries | map(select(.value != null)) | sort_by(.key)
      | map("\(.key)=\(.value|ascii_downcase)") | join("\n")' \
  | shasum -a 256
```

If the printed hash matches the one the checkout shows, the client is transacting against the canonical deployment. If it differs, stop — the addresses have been swapped.

Then map it into the SDK's address type in one call — the record keys are **not** the SDK's field names, and spreading a record verbatim leaves renamed fields `undefined`, silently:

```ts
import { addressesFromDeploymentRecord } from "@figaro-protocol/sdk";
const addresses = addressesFromDeploymentRecord(record);   // never { ...record }
```

Two keys are renamed (`figaroCore → core`, `tokenAddress → token`), five carry no SDK field (`florinToken`, `swapQuoter`, `permitTokenAddress`, `chainId`, `deploymentBlock`), and every other address key passes through under its own name. Only a missing `figaroCore` throws; every unknown key is ignored, never an error. Start every `getLogs` scan at the record's `deploymentBlock` — there are no getters to fall back on, so the event log is the read path, and scanning from block `0` on a public network is a great deal of range for nothing.

The audit scope, its baseline commit and the change policy for a change inside it are in [`docs/AUDITOR_HANDOVER.md`](https://github.com/figaro-protocol/Figaro/blob/main/docs/AUDITOR_HANDOVER.md).
