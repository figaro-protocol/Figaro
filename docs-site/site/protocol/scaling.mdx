Two resolution paths, one set of rules — `FigaroCore`'s. Both carry the same two operations — **commit** and **resolve** — and they share no state.

Read the [whole model](/) first, and [The contracts](/protocol/contracts/) for the surfaces named below.

- **The direct path** is the always-available floor: each operation is a call to `FigaroCore` (`commit`, then the buyer's `resolveProcess`). No admin, no timeout, no escape hatch.
- **The batch path** is a throughput tier beside it: a validity proof applies many operations — commits *and* resolves alike — in one transaction against `FigaroBatchVerifier`. Everything the batch path resolves, the direct path could resolve on its own; the batch path only makes it cheaper.

## The two paths share no state

This is the single most important thing to hold. `FigaroCore` and `FigaroBatchVerifier` never call each other and share no storage. A process resolved through a batch advances the verifier's own `stateRoot`; it **never acquires `FigaroCore` status**. `core.orderStatus(orderHash)` returns `0` — UNKNOWN — for it, permanently. The converse holds too: a `FigaroCore`-resolved process is never inside a batch, and there is no migration between the paths.

What follows for a builder, mechanically:

- **Anything gated on `orderStatus` cannot see batched trade** — not "sees it late," cannot see it at all. This is the read-time [sharp edge](/protocol/sharp-edges/): fold both event streams, never one alone.
- **A reader must fold both.** An indexer or reward calculator that reads only `FigaroCore` events under-reports everything that scaled. The two streams are deliberately distinguishable — `FigaroBatchVerifier.Attestation` shares the coordinator's topic hash, so filter by contract address, not by topic.
- **Exactly one thing crosses the boundary:** the uses for designer rewards — each a (kind, key, process, seller) the guest proved — carried by `settleBatch` into `UsageCounter.applyBatchAccrual`, which counts them into the same tally a direct call feeds, never as `FigaroCore` state. Value crosses as net token positions — payment, not state. No status, no process, no attestation entry crosses.

## Depth is already solved — multi-process composition

Depth (a single process's order count) is bounded by gas: `resolveProcess` iterates every commitment in one transaction, so the ceiling is the chain's cap on one transaction's gas or the block's budget, whichever is smaller — about 550 orders under the cap mainnet enforces (EIP-7825's 2^24); the SDK reads the live limit and takes the cap, and no figure here is mainnet-stable. Practical assemblies stay well below it. Where more depth is wanted, an order in process A roots process B, each process linear and within the ceiling — an existing `FigaroCore` property, not a layer to build. `FigaroCore` sees only linear process chains; topology lives off-chain.

The batch path solves the other constraint, **throughput** — many concurrent processes competing for block space — by moving execution off-chain and landing only the proven net effect.

## How the batch path resolves

A prover executes many `FigaroCore` transitions off-chain and publishes a succinct proof that the resulting state root is reachable from the prior one under `FigaroCore`'s rules. On chain, `settleBatch` verifies the SP1 proof against an immutable program verification key, checks state-root continuity and chain binding, hash-verifies the auxiliary calldata, checks every spec binding — for each attestation sent in the plaintext form, the guest commits its clause key beside `keccak256` of the witness-spec bytes it validated content against, and the verifier requires the two equal and `ClauseRegistry.registered(clauseKey)` (`src/core/verifier/FigaroBatchVerifier.sol:601-609`), because a clause key is the hash of its spec's pinned bytes — reconciles net token positions, re-emits proven `Attestation` events, and forwards usage accrual. The verification key covers a **generic clause engine**, not a clause list — the registry anchors the constraint set — so a never-seen clause resolves through the proven path with zero code changes, exactly as it does on the direct path.

**A batched attestation sends hashes unless its party chooses otherwise.** By default it carries exactly what `AttestationCoordinator` takes on the direct path — the `clauseDataHash`, the inclusion proof and the `contentRef` — and the guest checks that the clause leaf opens against the order's signed `checkoutHash`, as the coordinator does, and commits no spec binding; the relay and any prover see the fingerprints the chain sees, and the verifier re-emits the coordinator's event byte for byte. A party that wants its content validated inside the proof sends the plaintext form — the spec, the content and the committed clauseData (`checkContentInProof` on the SDK's `SequencerClient`). The relay then receives that plaintext, and so does the Succinct Prover Network when the relay proves there (`SP1_PROVER=network`). The reserved provenance leaf is accepted on inclusion alone in the hash-only form, as on the direct path; the bytes behind it are checked where they are used, at the usage claim.

The batch path's structural advantage is **netting**: the prover aggregates all movements per `(token, wallet)` pair into a single net position, so a hundred buyers paying one seller in one token become one net position instead of a hundred transfers. `FigaroCore`'s nine invariants are preserved exactly — the proof enforces the same rules the Solidity `FigaroCore` does, at batch scale — and the external interface, the event semantics, buyer dominance, atomic resolution, and no-escape-hatches are unchanged.

Pre-commit funding composition is direct-path only: `WitnessSwapAndCommitCoordinator.swapAndCommit` supplies a bond and calls `FigaroCore.commit` in one transaction, and the batch wire format has no funding leg. The batch-path equivalent is a wallet-side swap before the signed commitment is submitted. Post-resolution routing is identical on both paths — both deliver by ERC-20 transfer to the party's own address.

## The sequencer is transport, not authority

A **sequencer** relay collects signed operations, assembles a batch, runs the prover, and calls `settleBatch` — which is permissionless, with no caller gate, so anyone who can produce the proof may land one. The relay's powers are to **delay** and to **censor**; it cannot withhold the state its batches are built on, because every batch it lands logs its whole operation stream and the Core's own order events. The batch path's EIP-712 domain names `FigaroBatchVerifier` as its `verifyingContract`, so a signature made for the batch path does not verify on `FigaroCore`: going direct means opening a new process on `FigaroCore`, signed for its domain, and any new process can always open there. A process already open on the batch path holds its bonds in the verifier and resolves only through a batch built on the state behind the verifier's root; the verifier stores only that root, and anyone rebuilds the state from the verifier's own logs (a relay started with `REBUILD_FROM_CHAIN=1`). The relay cannot fabricate operations (every one carries EIP-712 signatures verified inside the proof), steal tokens (movements are what the proof commits to), violate an invariant (a violating batch produces no valid proof), or forge state (the on-chain root chain rejects a proof against a fabricated prior state). Correctness needs no trust in the sequencer; only **liveness** does — a stopped relay delays the resolution of the processes open on the batch path, and any relay, rebuilt from the chain, can land it. `FigaroCore` is independent of every relay. The buyer resolves on the batch path by signing `ResolveProcess(bytes32 processId, uint256 cumulativeValue)` under the verifier's domain: the process's cumulative value as the buyer accepts it. The proof applies the resolve only while the process holds that value, so, whoever holds the signature, it pays exactly the prefix of the process whose cumulative value the buyer signed, every order of which the buyer co-signed. A later commit moves the value past it, and the buyer signs again over the new value; a value the process has not yet reached pre-authorizes exactly the orders that bring it there.

The relay exposes five endpoints. **Submission** — `POST /submit` (a signed `FigaroCore` operation: a commit, a resolve, or an attestation), `POST /submit-usage` (the usage claim: kind `0` a clause, kind `1` an assembly with the agreement's `agreementHash`, `slotContentHash` and membership proof, kind `2` a registered agreement with its assembly's `assemblyHash`; the relay drops a claim whose key its own kind's registry does not hold live, whose registry read fails, or that names a reserved key), the liveness reads `GET /health` and `GET /status`, and `GET /state`: the state behind the relay's root, which a party or a second relay saves to a new file and starts on once the `x-figaro-state-root` header matches the verifier's `stateRoot` — the relay recomputes the root and refuses to start unless it is the verifier's, so a copy is checked, never trusted. Never write a served state over a state file unchecked: a stale relay serves a stale state, and the file it replaces may be the only copy. **Reading batched trade** never goes through a relay: the verifier emits `FigaroCore`'s own `OrderCommitted`, `OrderSeller`, `OrderCurrency`, `OrderResolved` and `ProcessResolved` for every batched order, so the readers that read `FigaroCore`'s logs read the verifier's address beside it. The endpoint-by-endpoint request and response shapes are on the [SDK manual](/building/sdk/).

Running your own relay, as opposed to using one, is the one advanced path that is not public-surface-only — the proving apparatus is the repository's Rust workspace, and that boundary with its build-and-run recipe is stated once on [The contracts](/protocol/contracts/#the-two-paths-share-no-state). Because `settleBatch` is permissionless, a relay adds throughput, never trust.
