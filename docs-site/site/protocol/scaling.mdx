Two resolution paths, one kernel. Both carry the same two operations — **commit** and **resolve** — and they share no state.

Read the [whole model](/) first, and [The contracts](/protocol/contracts/) for the surfaces named below.

- **The direct path** is the always-available floor: each operation is a call to `FigaroCore` (`commit`, then the buyer's `resolveProcess`). No admin, no timeout, no escape hatch.
- **The batch path** is a throughput tier beside it: a validity proof applies many operations — commits *and* resolves alike — in one transaction against `FigaroBatchVerifier`. Everything the batch path resolves, the direct path could resolve on its own; the batch path only makes it cheaper.

## The two paths share no state

This is the single most important thing to hold. `FigaroCore` and `FigaroBatchVerifier` never call each other and share no storage. A process resolved through a batch advances the verifier's own `stateRoot`; it **never acquires kernel status**. `core.orderStatus(orderHash)` returns `0` — UNKNOWN — for it, permanently. The converse holds too: a kernel-resolved process is never inside a batch, and there is no migration between the paths.

What follows for a builder, mechanically:

- **Anything gated on `orderStatus` cannot see batched trade** — not "sees it late," cannot see it at all. This is the read-time [sharp edge](/protocol/sharp-edges/): fold both event streams, never one alone.
- **A reader must fold both.** An indexer or reward calculator that reads only `FigaroCore` events under-reports everything that scaled. The two streams are deliberately distinguishable — `FigaroBatchVerifier.Attestation` shares the coordinator's topic hash, so filter by contract address, not by topic.
- **Exactly one thing crosses the boundary:** the usage accrual for designer rewards, carried by `settleBatch` into `UsageCounter.applyBatchAccrual` as proved numbers, never as kernel state. Value crosses as net token positions — payment, not state. No status, no process, no attestation entry crosses.

## Depth is already solved — multi-process composition

Depth (a single process's order count) is bounded by gas: `resolveProcess` iterates every commitment, so the ceiling scales with the block gas limit — on the order of ~1,240 orders at a 30M-gas limit, ~8,260 at a 200M-gas limit; the SDK reads the live limit, and no figure here is mainnet-stable. Practical assemblies stay well below it. Where more depth is wanted, an order in process A roots process B, each process linear and within the ceiling — an existing kernel property, not a layer to build. The kernel sees only linear process chains; topology lives off-chain.

The batch path solves the other constraint, **throughput** — many concurrent processes competing for block space — by moving execution off-chain and landing only the proven net effect.

## How the batch path resolves

A prover executes many kernel transitions off-chain and publishes a succinct proof that the resulting state root is reachable from the prior one under the kernel's rules. On chain, `settleBatch` verifies the SP1 proof against an immutable program verification key, checks state-root continuity and chain binding, hash-verifies the auxiliary calldata, checks every `(clause key → witness-spec hash)` binding against `ClauseRegistry.contentHashOf`, reconciles net token positions, re-emits proven `Attestation` events, and forwards usage accrual. The verification key covers a **generic clause engine**, not a clause list — the registry anchors the constraint set — so a never-seen clause resolves through the proven path with zero code changes, exactly as it does on the direct path.

The batch path's structural advantage is **netting**: the prover aggregates all movements per `(token, wallet)` pair into a single net position, so a hundred buyers paying one seller in one token become one net position instead of a hundred transfers. The kernel's nine invariants are preserved exactly — the proof enforces the same rules the Solidity kernel does, at batch scale — and the external interface, the event semantics, buyer dominance, atomic resolution, and no-escape-hatches are unchanged.

Pre-commit funding composition is direct-path only: `WitnessSwapAndCommitCoordinator.swapAndCommit` supplies a bond and calls `FigaroCore.commit` in one transaction, and the batch wire format has no funding leg. The batch-path equivalent is a wallet-side swap before the signed commitment is submitted. Post-resolution routing is identical on both paths — both deliver by ERC-20 transfer to the party's own address.

## The sequencer is transport, not authority

A **sequencer** relay collects signed operations, assembles a batch, runs the prover, and calls `settleBatch` — which is permissionless, with no caller gate, so anyone who can produce the proof may land one. The relay's only powers are to **delay** or **censor**, and the fallback is always direct `FigaroCore` submission with the same signed artifacts. It cannot fabricate operations (every one carries EIP-712 signatures verified inside the proof), steal tokens (movements are what the proof commits to), violate an invariant (a violating batch produces no valid proof), or forge state (the on-chain root chain rejects a proof against a fabricated prior state). Correctness needs no trust in the sequencer; only **liveness** does — a stopped relay delays a batch's payout, never the kernel, which is independent of it. The wire protocol and read endpoints (which mirror the kernel events a batch-resolved order does not emit) are on the [SDK manual](/building/sdk/).

Running your own relay, as opposed to using one, is the one advanced path that is not public-surface-only — the proving apparatus is the repository's Rust workspace, and that boundary with its build-and-run recipe is stated once on [The contracts](/protocol/contracts/#the-two-paths-share-no-state). Because `settleBatch` is permissionless, a relay adds throughput, never trust.
